第 6 课：从 Transformer 到 LLM 全景图

前五课我们把 Transformer 拆到了零件级：注意力、位置编码、归一化、Tokenization、逐层参数。现在把镜头拉远——从"一个 7B 模型"扩展到"整个 LLM 家族"，看清参数量级、训练三阶段、推理两阶段、开源与闭源的分岔，以及模型能力的硬边界。

🎯 学完这 6 步你将能够：
① 说清 7B / 70B / 405B / 671B(MoE，即把前馈网络拆成很多个专家、每个 token 只激活其中少数几个) 的参数量与激活参数差别，并估算显存门槛
② 画出 LLM 从随机权重到"能对话"的三阶段训练流程，标出每阶段的数据量与算力占比
③ 解释为什么首字要等、后续越吐越快，并判断一个模型"标称上下文"与"有效上下文"的差距
🗺 本节推理链（6 步：从"参数量级"到"能力边界与学习地图"；其中第 4 步为选型支链）
1要判断一个模型能不能跑在自己的机器上，必须先分清"总参数"与"每 token 激活参数"——dense 模型两者相等，MoE 模型可以差约 18 倍（671B ÷ 37B），因此显存看总参数、算力看激活参数。
↓
2知道了规模，下一个问题是这些权重怎么来的——这就要求把训练拆成 预训练（学语言与世界知识）、后训练（SFT，即监督微调，教会模型听指令；DPO，即直接偏好优化，让模型对齐偏好）、长上下文扩展（把 token 窗口从 8K 撑到 128K）三段，于是才能解释"同一个基座为什么能变成不同助手"。
↓
3模型训好了要跑起来，而推理不是一次前向——因此必须区分 prefill（一次并行处理整段提示，计算受限，决定首字延迟）与 decode（一次一个 token，带宽受限，决定吐字速度），否则会误以为"加显卡就能让首字更快"。
↓
4【支链 · 选型维度】前三步都在讲"模型本身"，但工程落地还要回答一个正交问题：这套推理成本由谁承担——于是出现 开源权重与 闭源 API 两条路：前者数据不出域、边际成本低但要自己运维，后者开箱即用但按 token 付费、数据要出域。这就要求按成本、延迟、合规三个维度做选型，而不是比"谁分数高"。
↓
5选完模型还要知道它会在哪里翻车——因为 幻觉、长上下文失稳、多步推理衰减、无法自校验都是结构性限制而非待修的 bug，因此必须用检索（把外部真值片段作为 token 注入上下文）、工具调用、验证层去补，而不是靠"换个更好的提示词"。
↓
6把上面五步的结论收成一张地图：于是第一部分（认知衔接）到此闭环，接下来第二部分学 预训练（在万亿级 token 上做 next-token prediction）与对齐、第三部分学推理部署、第四部分学 Agent 工程——每一步都建立在本课这张全景图上。

同样是 Transformer，为什么参数量能从 1 亿跨到 2.78 万亿？
提示：先分清两个数——"总参数"和"每个 token 真正参与计算的参数"。想清楚这两个数在 dense 模型和 MoE 模型里是不是同一个数，答案就出来了。
▾
知识背景
参数量级是 LLM 的第一张名片：Llama 3.1 提供 8B / 70B / 405B 三档 dense 模型（Meta, 2024）；DeepSeek-R1 是 671B 总参数、每 token 激活 37B 的 MoE 模型；2026 年的旗舰已进入万亿级——Kimi K3 为 2.78T 总参数、每 token 激活约 104B（约 3.7%）。MoE（Mixture-of-Experts，混合专家）把 FFN 拆成很多个"专家"，每个 token 只路由到其中少数几个，于是"总参数"与"激活参数"解耦。

上一课我们逐层解剖了一个 7B 模型，把 6.74B 参数拆到了每一层。现在把镜头拉远：同样是 Transformer，为什么有的模型只有 1 亿参数，有的能到 2.78 万亿？因为决定"大小"的从来不是一个数——因此必须先分清两个口径，否则连"这个模型能不能跑在我的机器上"都答不出来。

关键在一个反直觉的事实：模型的"大小"有两个口径。可以把 MoE 模型类比成一家有 896 位专科医生的大医院——挂号时只叫其中 16 位进诊室，但医院里所有医生的编制都得占地方。这就是"总参数"（编制）与"激活参数"（进诊室的人）的区别。

为什么要费劲做这种稀疏结构？因为稠密模型每 token 都要把全部参数算一遍：同样 671B 参数的稠密模型，单 token 前向约 2 × 671e9 = 1.34 TFLOPs，而 MoE 只激活 37B（约 74 GFLOPs）——差约 18 倍。MoE 正是用「多存参数、少算参数」把大模型的推理算力压下来。

模型架构总参数每 token 激活激活占比

Step 2：为什么 MoE 能"用 3.7% 的参数干活"
层Dense 模型MoE 模型（以 Kimi K3 为例）
Attention每层一份，全部参与每层一份，全部参与（不稀疏）
FFN每层 1 个，全部参与每层 896 个专家，路由选 16 个
每 token 计算量正比于总参数正比于激活参数（≈ 总参数的 3.7%）
MoE 只稀疏化 FFN（占参数大头），Attention 与归一化仍是稠密的——这就是为什么"激活参数"不会低到 1% 以下。
Step 3：显存门槛——总参数决定能不能装下
模型fp16 权重4-bit 量化权重消费级显卡能否单卡跑
7B≈14 GB≈4.0 GB能（8GB 显存起）
70B≈140 GB≈43 GB不能（需 2×24GB 或 A6000）
671B (MoE)≈1.3 TB≈404 GB不能（服务器级，约 8×H100-80GB）
权重显存 ≈ 参数量 × 每参数字节数（fp16 = 2 字节；4-bit 按 Q4_K_M 实测口径 ≈ 0.6 字节，含量化元数据开销，故高于理论值 0.5——如 7B 的 6.74B 参数 × 0.6 ≈ 4.0 GB，实测值见 TheBloke 的 GGUF 量化表）。注意：显存看总参数，算力看激活参数——MoE 省的是算力，不是显存。
🎯 关键认知

MoE 把"总参数"与"激活参数"解耦：总参数决定显存门槛，激活参数决定每 token 的算力成本。所以 671B 的 MoE 模型推理算力可能接近一个 37B dense 模型，但显存需求仍是 671B 级别——这就是为什么"MoE 让大模型变便宜了"这句话只对了一半。

为什么一个只会"预测下一个词"的基座，必须再训一遍才能听懂指令？
提示：先想"会预测下一个词"和"会听指令"是不是同一件事。如果不是，那中间必然有一步把前者变成后者——那一步用什么数据、花多少算力？
▾
知识背景
Llama 3 的训练分两大阶段（Meta, 2024）：① 预训练——在约 15.6T 多语言 token 上做下一个词预测，旗舰模型用了 3.8×10²⁵ FLOPs、最多 16K 张 H100；② 后训练——用 SFT（监督微调）+ RS（拒绝采样）+ DPO（直接偏好优化）把基座变成助手，而不是用更复杂的 RLHF（靠人给模型的回答打分、再用强化学习调整模型）。此外还有一次长上下文继续预训练，把窗口从 8K 扩到 128K。

上一张卡片我们看清了模型的规模。但规模只是"容量"，一个刚预训练完的模型只会做一件事：预测下一个词。它不会听指令、不会拒绝有害请求、也不会按格式输出——因为它的训练目标里根本没有"回答用户"这一项，所以必须再训一遍。

把这三段训练类比成培养一名医生：预训练是读完整个医学院（海量知识），后训练是规培（学会按规范问诊、写病历），长上下文扩展是进修（能一次看完一整套病历）。

这一步的必要性有一个经典反例：OpenAI 的 InstructGPT 工作中，13 亿参数的 1.3B 模型经后训练后，其回答被人类标注员偏好的比例超过了 1750 亿参数的 GPT-3 基座——参数量差 100 倍以上，赢的却是「听得懂指令」这一项（Ouyang et al., 2022, arXiv:2203.02155）。

Step 3：后训练为什么"便宜但关键"
方法需要什么数据解决什么
SFT（监督微调）指令-回答对让模型学会"按指令回答"的格式与风格

🎯 关键认知

预训练决定模型的能力上限（知道多少、能推多深），后训练决定模型的可用性（听不听话、格式对不对、安全不安全）。同一个基座 + 不同后训练 = 完全不同的产品——这就是为什么开源社区能基于同一个 Llama 基座做出几百个风格迥异的助手。

3
为什么同一个模型，首字要等两秒、后面却越吐越快？
提示：先想"处理 1000 个输入 token"和"生成 1 个输出 token"这两件事，哪个是算得多、哪个是搬数据多。瓶颈不同，优化手段就完全不同。
▾
知识背景
推理被拆成两个阶段（NVIDIA, 2026）：Prefill 一次并行处理整段提示、填充 KV Cache（把已算过的键和值存下来复用），是计算受限（compute-bound），决定首字延迟 TTFT；Decode 一次只生成一个 token，每步都要把全部权重和不断增长的 KV Cache 从显存读一遍，是带宽受限（memory-bound），决定每 token 延迟 TPOT。判据是算术强度（Arithmetic Intensity = FLOPs ÷ 访问字节数）与硬件的 ridge point 之比。

上一张卡片讲完训练，现在模型要上线服务了。用户按下回车后，会经历两段体感完全不同的等待：首字延迟（等第一个字出来）和吐字速度（后面每个字多快）。因为这两段落在 GPU 性能曲线的两侧，所以优化手段完全相反——先判断瓶颈在哪一侧，再决定加什么。

这两段类比成餐厅出餐：prefill 是"一次性把整桌菜备齐"（后厨火力全开，比的是灶台功率），decode 是"一道一道端上桌"（比的是传菜通道有多宽，灶台反而闲着）。

🧮 两阶段账：算术强度与瓶颈判定
Step 1：两个阶段在做什么
阶段一次处理多少 token瓶颈决定什么指标
Prefill整段提示（如 2048 个）计算（Tensor Core 打满）TTFT（首字延迟）
Decode1 个（每步）显存带宽（HBM 打满）TPOT（每 token 延迟）
两阶段用的是同一套权重，但落在 GPU roofline 的两侧——这就是"同一个模型两种瓶颈"的根源。
Step 2：算术强度——用数字判定瓶颈
阶段算术强度（FLOP/byte）与 ridge point（≈295，以 H100 SXM 为例：989 TFLOPS ÷ 3.35 TB/s ≈ 295）比较结论
Prefill≈ 提示长度 S（如 S=2048 → ≈2048）远高于 ridge计算受限
Decode≈ 批大小 B（B=1 → ≈1）远低于 ridge带宽受限
算术强度 = 总 FLOPs ÷ 总访问字节数。高于 ridge point 说明"算得比搬得快"，瓶颈在算力；低于则说明"搬得比算得慢"，瓶颈在带宽。prefill 一次处理 S 个 token，每读一次权重能算 S 次，故强度 ≈ S；decode 每步只出 B 个 token，故强度 ≈ B。两者在长提示下可差 3 个数量级。
Step 3：为什么"加显卡"救不了首字延迟
TTFT 的组成部分占比量级（二手/估算，随场景浮动、非同一时刻相加）加显卡能改善吗
排队等待常为首要项否（要靠调度与扩容策略）
KV Cache 传输（PD 分离时）PD 分离时可居首否（受互联带宽限制）
Prefill 计算本身约 2%~23%（二手，需人工核实）是（但只影响这一小块）
这是最反直觉的一条：首字延迟的大头往往不是算得慢，而是排队和搬 KV Cache。所以优化 TTFT 的第一手段是调度与架构（如 PD 分离、前缀缓存），而不是换更快的卡。
🎯 关键认知

推理优化的第一步永远是先判断瓶颈在哪一侧：decode 阶段 Tensor Core 利用率常常只有个位数百分比，显存带宽却已打满——此时加算力毫无用处，该做的是减少每步要搬的字节数（KV Cache 量化、GQA（把多个 Query 头分成几组、每组共享同一份 K/V）/MLA（把 K/V 压缩成一个更小的向量、用时再还原）、投机解码提高算术强度）。

知识背景

5
模型"看起来很懂"，为什么还会一本正经地胡说？
提示：先想模型在做什么——它是在"查事实"还是在"预测下一个最像的词"。如果它没有查证能力，那"不知道"的时候它会怎么办？
▾
知识背景
幻觉不是待修的 bug，而是训练目标的结构性后果：模型被训练成"预测下一个最可能的词"，而评测又奖励"猜"而不是"承认不知道"（Kalai et al., 2025）。关于"不知道时会不会编造"，目前只有 2026 年的第三方二手数据，且各来源口径不一致（需人工核实）：Artificial Analysis 的 AA-Omniscience 基准被聚合来源引作"Gemini 3 Pro 幻觉率约 88%、准确率约 55.9%，Gemini 3 Flash 约 91%"；另有开发者论坛贴记为"Gemini 2.5 Pro 约 88%、Gemini 3 Pro 准确率约 53%"。同一指标被挂到不同代际模型上、准确率也对不上，说明这些数字尚不可靠，只能当趋势看。此外还有多步推理衰减、无法自校验、无法区分"指令"与"被读的数据"等结构性限制。

上一张卡片我们选好了模型。但上线前必须知道它会在哪里翻车——否则第一次事故就会教你。

把模型类比成一位口才极好但从不查资料的专家：他讲得头头是道，但被问到不熟的领域时，他不会说"我不确定"，而是顺着话头编一个听起来最合理的答案——因为他的训练目标就是"说出最像正确答案的话"。

要压住这类编造，工程上常见的做法是 RAG（先去外部知识库检索相关材料、再让模型照着检索结果回答）与工具调用。

这些边界不是猜测，都有论文与实测支撑：字符级计数的失败被归因于 tokenizer（把文本切成 token 的组件，模型看不到字符本身）——「strawberry 里有几个 r」自 2024 年起被广泛讨论（Karpathy, 2024；arXiv:2410.14166）；中间遗忘由 Stanford 提出的 Lost in the Middle（即「迷失在中间」，Liu et al., 2023, arXiv:2307.03172）用 U 形曲线量化；知识截止来自训练数据被冻结，多步衰减来自误差的乘性累积，无法动手则来自模型只能输出文本这一事实。

上一张卡片我们看到模型会一本正经地胡说（幻觉）。但幻觉只是「看起来懂却不可信」的一种表现；把镜头再拉远一层，还有一批事是这一代大模型在原理上就做不到的——不是提示词没写好，也不是没喂数据，而是它的输入/输出形式、注意力机制、训练数据边界共同决定的。

打个比方：模型只认 token、没学过字符，也没长出手脚——读得再流利，也数不清一句话里有几个字母，更没法替你按下发送键。下面把这类事列成一张清单，并逐条标出「后面哪一课解决它」，它同时就是这一部分的学习地图。

🤔 学生最可能追问的 5 个问题
1.为什么模型数不清 strawberry 里有几个 r？换个更大的模型能解决吗？▾

因为模型从来没见过「字符」这个单位。

对象数量 / 单位说明
strawberry 的字母数10 个字符s-t-r-a-w-b-e-r-r-y
其中字母 r 的个数3 个第 3、8、9 个位置
模型实际拿到的约 2~3 个 token如「straw」+「berry」，看不见内部字母

模型只能看到 token 的编号，看不到 token 内部的字母——所以它是「猜」有几个 r，而不是「数」。这属于单位不对的结构性问题，换更大的模型只能改善、不能根治：再大的模型也还是 token 输入。

可靠做法是把计数外包给代码执行（让模型写一行 len([c for c in 'strawberry' if c=='r']) 再运行），这正是《工具调用》要教的。顺带一个数字：同一个词，token 数（约 2~3）与字符数（10）并不相等——这也是按 token 计费时长度对不上的原因。


2.长上下文里「中间遗忘」到底有多严重？关键信息放中间会差多少？▾

用一个受控实验看：同一批文档，只把「含答案的那一篇」挪位置，其余不变。

答案文档的位置模型答对的相对水平原因
开头（首因）高最先进入注意力
中间（第 5~15 篇附近）明显最低被前后大量内容稀释
结尾（近因）高离生成位置最近

Stanford 的 Lost in the Middle（Liu et al., 2023, arXiv:2307.03172）正是用「20 篇文档、约 4K token」这个设定画出 U 形曲线的：两端高、中间低。原文图 1 的具体百分点随模型与文档数变化，这里只作定性描述，精确数值需核对原论文（人工核实）。

工程结论：不要以为「把资料全塞进上下文」等于「模型会用」。要么把关键信息放首尾，要么用检索只喂最相关的少数几篇——这就是《记忆与 RAG 工程化》要解决的。


3.既然知识停在训练截止日，那用微调把最新知识灌进去行不行？▾

可以，但通常不划算。要区分「补新知识」和「改行为」。

需求首选手段原因典型代价
补最新事实（新闻、价格）检索（RAG）改一次文档库即可，秒级生效只改 1 份文档
补私域文档（内部手册）检索（RAG）数据不出域、可溯源建 1 次索引
改风格 / 格式 / 语气微调这是行为，不是事实需千级样本、重训数小时
灌入海量新知识不推荐微调易遗忘、难溯源、更新要重训每次更新都要重跑

一句话：知识用检索补（时效以分钟计），行为用微调改（周期以天计）。所以模型「不知道训练之后的事」并不致命——只要给它一个能实时更新的外部知识库，这就是《记忆与 RAG 工程化》的核心。


4.单步 95% 正确，为什么多步任务还是经常做不完？▾

因为误差是乘性累积的，不是加性的。

步数单步 95%单步 99%
1 步0.9500.990
5 步≈0.774≈0.951
10 步≈0.599≈0.904
20 步≈0.359≈0.818

算式：综合正确率 ≈ 单步正确率步数。0.95¹⁰ ≈ 0.599——十步之后只剩约 60%；即使单步高达 99%，十步后也只有约 90%。更麻烦的是，模型往往不会回头纠正已经出错的中间步骤，反而顺着错下去。

对策不是「让它再检查一遍」（检查本身也是一步），而是把每一步锚定到外部真值：用代码执行算、用检索查事实、用工具返回结果。这正是《推理模型与 RLVR》和《从 Prompt 到 Agent》的主题。


5.模型既然不会「动手」，工具调用是怎么让它真正做事的？▾

关键：模型始终不执行动作，它只输出一段结构化指令，由你的程序去执行。

步骤谁做做什么
1你的程序把工具清单（名字 + 参数格式）连同问题发给模型
2模型判断需要工具，输出 JSON：调用哪个函数、参数是什么
3你的程序真正执行（发邮件、查数据库…），拿到结果
4模型把结果组织成自然语言回答

所以模型像一位只出主意、不动手的项目经理：它负责调度工具，执行权始终在你的代码手里。顺带一个性能数字：查 10 个城市的天气，串行调用要 10 轮对话（每轮约 2 秒）共约 20 秒，并行调用只需 1 轮约 2 秒——约 10 倍差距。

这既补上了「不能动手」这条边界，也带来新风险：模型分不清「指令」和「读到的数据」，这就是《工具调用》与 Agent 安全要处理的问题。
