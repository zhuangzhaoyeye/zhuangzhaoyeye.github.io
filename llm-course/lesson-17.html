第 17 课：微调工程

前面几课我们一直在"把模型跑起来"——切分、省显存、量化。这一课换个目标：把通用模型调成你自己的助手。但全量微调在显存上先撞墙（7B 要 112 GB），于是有了 LoRA（即冻结基座、只训一对低秩矩阵）。这一课把 LoRA 的显存账、三个旋钮、QLoRA（即把冻结的基座也用低精度存、再训一小对适配器）的三件套算清，最后回答一个比"怎么调"更重要的问题：什么时候该微调、什么时候该用检索、什么时候改提示词就够了。

🎯 学完这 6 步你将能够：
① 拆开全量微调的 16 B/参数，说清为什么"贵在状态不贵在权重"
② 用 ΔW = BA 算出 LoRA 把参数量压到了几分之一，并理解 rank / alpha / target_modules 各在调什么
③ 算清 QLoRA 三件套各省多少，并给出"该微调、该 RAG（即检索增强，把外部资料检索出来塞进上下文）、还是该改提示"的判断
🗺 本节推理链（6 步逻辑递进：从"显存账"到"三选一决策"）
1要把一个 7B 基座调成客服助手，必须先把全量微调的显存账算清——这就要求知道 16 B/参数里权重只占 2 B，其余全是 gradients 与优化器状态。全量的成本在状态不在权重。
↓
2既然「全量的成本在状态不在权重」，所以真正要砍的是"为每个参数维护的梯度与优化器状态"——于是LoRA 冻结基座、只训一对低秩 projection（低秩投影）矩阵 A 与 B，参数量因此降三个数量级。只学低秩的增量。
↓
3既然「只学低秩的增量」，所以能省多少、能学多少就取决于三个旋钮——因为rank 决定容量、alpha 决定更新幅度、而覆盖哪些 attention 层的投影决定能改多少行为。覆盖面往往比 rank 更重要。
↓
4「覆盖面往往比 rank 更重要」讲的是怎么调旋钮；但无论怎么调，LoRA 能省的始终只是「要更新的那一小部分」——被冻结的基座仍以 bf16 全量躺在显存里（65B 就是 130 GB）。这就要求连基座本身也别再占 bf16——于是QLoRA 把基座用 4-bit 存、仍用 16-bit 算，gradients 只回传给适配器。基座也用低精度存。
↓
5既然「基座也用低精度存」，所以还要追问这只够不够——因为低秩是结构性约束，在要"学新知识"的 token 规模任务上会输给全量微调。低秩有能力的上界。
↓
6既然「低秩有能力的上界」，这就要求在它够不到时先定位失败的原因——因为缺知识还是缺行为，决定了该换哪件武器：缺知识就交给检索（往 context 里塞资料），缺行为才动权重。先分清缺知识还是缺行为。

1
想把 7B 调成客服助手，为什么"把全部参数都训一遍"在显存上就走不通？
提示：别只算权重——把训练时"每个参数要额外维护什么"也一起算进去，再乘上参数量。
▾
知识背景
全量微调的显存账在第 14 课已经拆过：16 B/参数 = 权重（bf16 2）+ 梯度（bf16 2）+ 优化器状态（fp32 master 4 + Adam 一阶 4 + 二阶 4 = 12）。LoRA（Hu 等，arXiv:2106.09685，2021）从这个账出发，指出"部署多个微调实例，每个都带全部参数，成本高得离谱"，于是冻结预训练权重、只注入可训练的低秩分解矩阵。QLoRA（Dettmers 等，arXiv:2305.14314，NeurIPS 2023）给了一个更极端的对照读数：16-bit 全量微调一个 65B 模型需要 >780 GB 显存。

前几课我们把模型"跑起来"了；从这一课开始，我们把它调成自己的。第一步不是讲方法，而是先把"为什么必须换方法"算成数字。

很多人的直觉是"微调要存模型权重，所以显存 ≈ 模型大小"——这个直觉错得很远。训练时每个参数要额外背两样东西：它的梯度 gradients，以及优化器为它维护的状态（Adam 有两份动量，再加一份高精度主权重）。三项加起来，一个参数在训练时要占 16 字节，而它本身只有 2 字节。这就像搬一次家：真正要带走的东西不多，但为了搬运，你得给每件家具都配一辆手推车和一个临时仓储位。

更自然的估法是只按权重算：7B 权重 7e9 × 2 B = 14 GB，一张 80 GB 卡看着绰绰有余；可一旦把梯度与优化器状态算进来，同一个模型要 7e9 × 16 B = 112 GB，比 80 GB 卡还多出 32 GB——「按权重估」这套更省事的算法，正是全量微调撞墙的第一个原因。

算出这笔账，才会明白"全量微调"三个字在显存上意味着什么。

算术：175e9 × 2 = 350e9 B = 350 GB/份。全量微调的深层代价不是"训一次"，而是训完之后每个任务都要独立存一份完整模型——这也是 LoRA 论文开篇点出的部署困境。
🎯 关键认知

全量微调撞墙的根因有两层：训练时贵在状态（16 B/参数里 12 B 是优化器与 master），部署时贵在副本（每个任务一份完整权重）。所以任何"省"的办法都必须同时回答这两问——下一张卡片的 LoRA，正是从砍掉大部分参数的梯度与优化器状态入手。

不学整个 ΔW，只学两个小矩阵相乘（ΔW = BA），凭什么不丢信息？
提示：先算全量更新矩阵有多少个数，再看 BA 这两个小矩阵能表示多少个方向。
▾
知识背景
LoRA 的做法是：冻结 W₀，把更新写成低秩分解 W = W₀ + ΔW = W₀ + BA，其中 B ∈ Rd×r、A ∈ Rr×k、r ≪ min(d, k)。论文的两个实现细节很关键：B 初始化为 0、A 用随机高斯初始化——这样训练开始时 ΔW = BA = 0，模型行为与基座完全一致，不会一上来就被破坏。LoRA 论文还报告：在 GPT-3 175B 上，即使满秩高达 12,288，极低的秩（r = 1 或 2）就已足够；相比 Adam 全量微调，可训练参数减少 10,000 倍、显存需求减少 3 倍。

上一张卡片算清了全量微调为什么贵。这一张回答 LoRA 的核心疑问：既然要学"这个任务带来的改变"，为什么不直接学整个 ΔW？

关键在于"改变"这件事本身有多大。因为基座已经把语言能力学完了，微调要注入的往往只是少数几个方向上的调整——格式、语气、领域术语。这类改变不需要动用 4096 × 4096 那么大的自由度——就像调一张照片往往只用几个滑块（亮度、对比度、色温），而不是逐个像素去改；要注入的改变只落在少数几个方向上。用矩阵语言说，就是要求更新矩阵 ΔW 的秩很小。

直接学整个 ΔW 的代价是实打实的：一个 4096×4096 投影就有 16,777,216 个数，每个都要背梯度与优化器状态——这正是上一张卡片 112 GB 里最贵的那部分。低秩之所以「不丢信息」，不是因为压缩掉了精度，而是因为要注入的改变本来就只占少数几个方向；只有当任务本质上需要满秩改写时，低秩才会真的够不到——这条边界留到第 5 张卡片展开。

还有一个反直觉点：rank 不是越大越好。参数量随 rank 线性涨——同一个 4096×4096 投影，r=1 时 8,192 个、r=64 时 524,288 个（涨 64 倍）；而且低秩约束本身就是一种正则，盲目加大 rank 等于放大自由度、在数据有限时更容易过拟合（LoRA 综述 arXiv:2407.11046 明确「higher is not always better」，过大的 rank 会造成性能与效率双重退化）。

把"只沿少数方向走"写成矩阵语言，就是令 ΔW 的秩很小——下面把数字算出来。

🎯 关键认知

LoRA 不是"近似地学一遍全量"，而是换了一个受约束的参数空间：它假设"任务需要的改变落在少数方向上"。这个假设在指令微调上通常成立（所以能 256 倍地省），但它也是一个能力上界——改变如果本质上需要全秩，LoRA 就够不到（第 5 张卡片展开）。B 初始化为 0 这个细节也别忘了：它保证训练从"等于基座"出发，而不是从随机扰动出发。

同样是 LoRA，为什么别人 r=8 就够、你的 r=64 还不如人家？
提示：别只盯着 rank——另外两个旋钮（更新的缩放、以及把 LoRA 加在哪些层上）常常影响更大。
▾
知识背景
LoRA 的输出是 frozen_out + (α / r) × BA：α 是 lora_alpha，缩放因子取 α / r。常见实践默认把 LoRA 加在 Q、V 投影上、并以 rank = 8 为起点（PyTorch 的 torchtune LoRA 教程即以 lora_attn_modules=["q_proj","v_proj"]、r=8 举例；docs.pytorch.org/torchtune/stable/tutorials/lora_finetune.html）；而一些实验发现，把 LoRA 加到自注意力（attention）的所有线性层、并把 rank 提到 16 或 32 可能更有益（只要保持 rank 远小于嵌入维度，显存影响相对较小）。实践里 α = 2r 是常见基线（r=8 → α=16），dropout 常取 0.05 ~ 0.1。

上一张卡片把 LoRA 压缩到 256 倍；这一张回答一个更常见的困惑：为什么同样的 LoRA，别人调得动、你调不动。

因为LoRA 不是一个参数，而是三个旋钮的组合：rank（多大容量）、alpha（更新缩放多大）、target_modules（改哪些层）。这三者的影响并不均等——只调 rank 而忽略另外两个，很容易出现"rank 翻了几倍、效果却没变"的情况。可以把它类比成调音台：推子（alpha）决定音量大小，通道数（rank）决定能同时处理多少路信号，而"接哪几路输入"（target_modules）决定你改的是主唱还是伴奏。

下面把三个旋钮各自在调什么、以及影响排序算清楚。

🧮 第三笔账：三个旋钮的量化影响

算术：真正进入前向的是 α ÷ r，不是 α 本身。所以 α 和 r 要一起看：r 从 8 提到 16 时若 α 不变，缩放就从 2 掉到 1，更新被削弱一半——这就是"rank 调大了却没效果"的一个常见原因。α = 2r 之所以流行，是因为它让"每个 rank 维度的贡献"保持在 2 倍，换 rank 时不必重调学习率。

Step 3：dropout 与学习率是配套的
旋钮常见取值作用
lora_dropout0.05 ~ 0.1防过拟合（小数据集尤其重要）
learning rate1e-4 ~ 2e-4比全量微调大（可训参数少，容忍更大步长）
训练轮数1 ~ 3 轮轮数一多，适配器就开始过拟合
这三项与第 10 课的"灾难性遗忘缓解手段"是同一套：LoRA + 低学习率 + 1~3 轮 + 混合通用数据重放。区别在于 LoRA 本来就限制了更新空间，所以它天然比全量微调更不容易把通用能力带偏。
🎯 关键认知

三个旋钮里，target_modules（覆盖面）与 alpha/r（缩放）常比 rank（容量）更值得先调——这是工程经验，不是 LoRA 论文的定量结论（论文消融里只加 Wq、Wv 已可得最佳）。只加 Q、V 与加全部线性层，差距往往比 rank 从 8 调到 64 更大——这也是"别人 r=8 就够"的原因：他们把 LoRA 铺得更广。调参顺序建议：先把覆盖面和 α/r 定下来，再按验证集曲线决定要不要加 rank。

提示：省掉的只是"要更新的部分"——那些没被更新的参数，训练时还要不要占显存？占多少？
▾
知识背景
QLoRA（Dettmers 等，arXiv:2305.14314，NeurIPS 2023）的三件套都有明确出处：① 4-bit NormalFloat（NF4）——把 16 个量化档位放在标准正态分布的分位点上，对正态分布的权重是信息论最优的数据类型；② 双重量化（Double Quantization）——把量化常数本身再量化一次，块大小 64、常数用 FP32 时是 32/64 = 0.5 bit/参数，双重量化后降到 8/64 + 32/(64×256) ≈ 0.127 bit/参数，平均省约 0.37 bit/参数（65B 约 3 GB）；③ 分页优化器（Paged Optimizers）——用 NVIDIA 统一内存把优化器状态在显存吃紧时自动换到 CPU。结果：65B 从 >780 GB 降到 <48 GB，Guanaco 65B 在 Vicuna 基准上达到 ChatGPT 的 99.3%。

上一张卡片把 LoRA 调好了；这一张回到 65B 这个量级——为什么只训千分之几，还是训不动？

因为LoRA 省掉的只是"要更新的那部分"，被冻结的基座仍然以 bf16 全量躺在显存里：65B × 2 B = 130 GB，光基座就超过任何单卡。更自然的想法是「可训练参数都压到千分之几了，显存不该再是问题」——但可训练的那部分只有约 3.2 GB，真正压在显存上的是这 130 GB 冻结基座。所以 QLoRA 的思路是：让冻结的那部分也用低精度存。这不是新算法，而是"4-bit 存储 + 16-bit 计算 + LoRA 训练"的组合——权重存成 NF4，用到时反量化回 bf16 参与计算，梯度（gradients）只回传给适配器，基座始终保持冻结。这就像搬家时把不用的家具先压缩打包（4-bit 存），真正要用时再拆开还原（反量化回 bf16）——省的是存储空间，不是搬运精度。

LoRA 这么省，是不是永远用它就行了？
提示：想一想第 2 张卡片里"低秩是能力上界"那句话——什么任务需要的改变，本质上不是低秩的？
▾
知识背景
这个问题有直接的实证研究：LoRA Learns Less and Forgets Less（Biderman 等，arXiv:2405.09673，2024）。它的结论是——在代码与数学任务上，无论是继续预训练（CPT）还是指令微调（IFT），低秩的 LoRA 都不如全量微调；但在 Tülu-v2-mix 这类通用指令数据上，LoRA 与全量微调持平。同时它观察到：LoRA 的遗忘比全量微调更少，而且**遗忘程度与 rank 正相关**（rank 越大，学得越多、忘得也越多）。

上一张卡片解决了"放不下"；这一张回答一个更容易被忽略的问题：LoRA 省下来的那些能力，是不是真的没代价？

因为LoRA 把更新限制在低秩子空间里，它就有一个天然的能力上界：如果某个任务需要的改变本质上不是低秩的，LoRA 再怎么调 rank 也够不到。这就像给房间重新刷墙——贴墙纸（低秩调整）很快，但要改承重结构（全秩改写）就不是贴纸能解决的了。Biderman 等的研究把这条界线画得很清楚：学"行为"（指令跟随、格式、语气）LoRA 够用；学"新知识"（代码、数学这类要在 token 规模上注入新知的继续预训练）全量更强。

更要紧的是第二半：LoRA 省的是"改变的幅度"，换来的恰恰是"不容易忘"。所以它不是一个纯粹的妥协，而是学习与遗忘的交换。

🎯 关键认知

LoRA 不是"更省的全量微调"，而是一次明确的交换：用"只能学低秩改变"换来"参数量降三个数量级 + 更不容易遗忘"。判据一句话——任务是学行为（IFT）还是学新知识（CPT）：前者 LoRA 通常够用甚至更好（还不容易忘）；后者全量微调明显更强，LoRA 调 rank 也只是逼近它的代价。别把"LoRA 更省"误读成"LoRA 更好"。

提示：先分清"它不知道"还是"它不照你说的做"——这两件事，一个改资料、一个改权重。
▾
知识背景
业界已形成一条分层的经验路径：先用提示词（改指令）→ 需要最新事实与可溯源就加检索（RAG，把资料塞进 context）→ 只有在需要"稳定的行为/格式/风格"时才微调。判据是"微调改变的是模型行为，而不是给它灌新知识"——想让模型知道最新价格，把价格表放进上下文通常就够了；想让它每次都输出固定 JSON 或固定语气，才需要动权重。另一头是部署：LoRA 论文指出部署时可把适配器合并进权重（无额外延迟），而多适配器场景有专门系统——S-LoRA（arXiv:2311.03285）报告可在单卡或多卡上同时服务上千个适配器，而朴素的"每适配器一份权重"方案受显存限制只能服务个位数。

前面五张卡片都在讲"怎么微调"；这一张回答更前面的问题：到底该不该微调。

因为微调改变的是模型的行为（语气、格式、思维方式），而不是给它"查资料"的能力——所以"模型不知道我们公司的最新产品"这类问题，微调通常不是正确答案。这就像对待一个新员工：如果问题是"他不知道公司的最新制度"，你应该给他一份手册（把资料放进上下文）；如果问题是"他说话总是不符合客服规范"，那才需要培训他的表达习惯（动权重）。把这两件事弄混，常见的代价是花几个月微调一个本该用检索解决的系统。

更自然的反应是「答不对就补训练」，但先做一次最便宜的判别：把正确的资料放进上下文，它能答对吗？能——那缺的是知识，这是一道检索题；不能——才轮到微调。跳过这一步，就会用一次训练去解决一个检索当天就能解决的问题。
