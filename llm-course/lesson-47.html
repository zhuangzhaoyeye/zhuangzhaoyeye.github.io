A2AAgentCardMCPAgent Skills标准生态互通
1
一个团队里有好几个 agent，各管一摊、各有各的工具，可它们互相看不到对方会什么。要让它们互相用上对方的能力，最省事的做法是什么？
提示：想一想有没有比「两两之间都单独接一根线」更省的做法。
▾
知识背景
当 agent 数量超过 1 个，「互通」（interoperability，两个系统能互相理解并调用对方的能力）就从可选项变成必答题。点对点连接（每个 agent 都要为其余每个 agent 单独写一个适配器，A→B、B→A 各一个）是直觉解法，但连接器数量随 agent 数**平方增长**——这正是「标准」存在的第一性理由：把「N 对 N」的网格坍缩成「每个 agent 只对接标准一次」。A2A（Agent2Agent）等开放协议就是干这个的。

前面几课把单个 agent 的「外壳」拆成 harness / rule / skill。这一课把视角拉到「很多个 agent」。

因为每个 agent 的能力和工具都封在自己那一亩三分地里，别的 agent 不知道、也用不上。就像十个人各有各的充电器，手机型号不同、插口不一样，你要借电还得再买一个转接头；要是大家都用同一个插口，就一根线搞定。所以下面算「点对点 vs 统一标准」的账。

🧮 第一笔账：点对点连接 vs 统一标准
Step 1：3 个 agent 各管一摊
agent能力别人能看到吗
A查订单不能
B查库存不能
C开发票不能
3 个 agent、3 个能力，互相都看不见——要互通，就得让每个 agent 为其余每个 agent 各写一个适配器（A→B、B→A 各算一个）。
Step 2：点对点连接要几根线
方式算式连接数
点对点N×(N−1)3×2=6 根
统一标准N×13 根
算术：3 个 agent 每个都为另外 2 个各写一个单向适配器，要 N×(N−1)=3×2=6 个；大家都接到同一个标准上，只要 3 根。
Step 3：agent 涨到 10 个会怎样
agent 数点对点统一标准
36 根3 根
1010×9=90 根10 根
点对点的连接数按 N² 增长：10 个 agent 要 90 根，统一标准只要 10 根——差 9 倍。
🎯 关键认知

没有互通标准，agent 之间是「点对点」的网——3 个要 6 根线、10 个要 90 根，随 N² 爆炸；有了标准，大家都对接同一个插座，3 个只要 3 根、10 个只要 10 根。这就是「标准」存在的第一性理由：把 N² 的网格坍缩成 N 条对标准线。

互通不是一件事，是三件——连（MCP）、会（Skills）、通（A2A），三个正交标准各管一维。要是硬用一个标准全包，三个维度挤在一起会又大又僵、改一处动全身；分成三个，各管一维、可单独替换，这才符合「正交设计」的第一性原理。

知识背景
A2A（Agent2Agent 协议，Google 发起、已捐给 Linux Foundation、现为 AAIF 旗下 Growth Stage 项目、Apache 2.0 许可，v1.0 于 2026 年 3 月发布）管 agent 之间的能力发现与任务委托。它的核心机制是 AgentCard——一张放在 `/.well-known/agent-card.json` 这个固定路径上的 JSON「数字名片」，写清「我是谁、会什么、怎么连、能做什么」；客户端有三种方式找到它（well-known 路径、注册表/目录、直接配置），找到后可用三种绑定通信（JSON-RPC 2.0 / gRPC / HTTP+JSON/REST）。

上一张把「通」归给了 A2A。这一张钻进 A2A 的核心——agent 怎么「发现」彼此。

知识背景
三个标准是**按需组合**的，不是「要么全上、要么不上」。判断依据是任务里实际出现哪几个维度：只连一个工具 → 只要 MCP；要把一套「怎么做」沉淀复用 → 加 Agent Skills；要让多个 agent 互相委托 → 再加 A2A。这是「最小必要标准」原则——用最少的协议解决当前问题，复杂度随需求涨，而不是一上来就上全套。

上一张讲清了 A2A。这一张回到选型：三个标准该用几个。

因为标准不是免费的——每多一个协议，就多一份实现和运维成本。就像你修个台灯只用一个螺丝刀，不会把整个工具箱都搬出来；可要修一整套电路，才需要那套齐全的家伙。所以下面按「任务里出现几个维度」来配标准。

5
既然标准有成本，那什么情况下干脆一个标准都不用、直接写代码就完了？「上标准」和「直接写代码」的分界线在哪？
提示：想一想这件事这辈子做几次、要不要给别人用。
▾
知识背景
标准（MCP / Agent Skills / A2A 这三个开放标准）解决的是「跨边界、反复发生」的问题，代价是「多一层抽象」。当任务是**一次性**、**单方**、**内部**时，这层抽象纯属负担——直接写代码更快、更清晰。判断口诀：**复用次数 N 和边界数 B 决定值不值得上标准**——一次性（N=1）且不跨边界（B=1）的任务，直接写代码；跨团队、反复用（N 大）的任务，才值得为标准付抽象成本。

上一张说「按需组合」，这一张问更极端的问题：什么时候一个都不用。

因为标准 = 多一层抽象，抽象本身要付成本。就像你写张便条提醒自己「明天交房租」，不会为此去注册一套日历同步协议——写一行字就完了。所以下面算「复用次数」这笔账。

🧮 第五笔账：标准 vs 直接写代码

任务复用次数做法
临时取一次数1 次写死代码
长期反复的接口100 次上标准
一次性任务写死代码最省；只有反复用的才值得为标准付抽象成本。
Step 2：抽象成本 vs 复用收益
情形抽象成本复用收益
N=1 次接标准花 100省 0（只用 1 次）
N=100 次接标准花 100省 100×10=1000
算术（示意值）：接一次标准花固定成本 100；复用 1 次省 0、复用 100 次省 1000——N 越大越划算。
Step 3：分界判据
判据直接代码上标准
复用次数N=1N 大
跨边界吗不跨（内部）跨团队/平台
分界：一次性 + 不跨边界 → 直接代码；反复 + 跨边界 → 上标准。
🎯 关键认知

标准解决「跨边界、反复发生」，代价是「多一层抽象」。一次性、单方、内部的任务，直接写代码更省（接标准花 100、只复用 1 次省 0）；跨团队、反复用的任务才值得付抽象成本（复用 100 次省 1000）。硬给「临时取一次数」上标准，是为一次性的活背上长期的协议负担。
