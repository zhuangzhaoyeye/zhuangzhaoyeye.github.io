第 48 课：四种设计哲学与选型

第 47 课讲清了三个开放标准（MCP 连 / Skills 会 / A2A 通），但标准只定义「接口长什么样」，不决定「agent 怎么被编排运行」——那是 harness（运行时）的活。同一套标准，四家主流的 harness 却长得不一样，因为它们各把一样不同的东西当「第一公民」。这一课把四种设计哲学讲透——Claude Code 的 context-first、OpenAI 的 agent-first、Google ADK 的 runtime-first、LangGraph 的 state-first——最后收口：按你的瓶颈选，而不是按名气选。

🎯 学完这 6 步你将能够：
① 说清「设计哲学」是什么：一家 harness 把什么当「第一公民」（其余一切都围着它转）
② 讲清四种哲学各把什么当第一公民：Claude Code=context、OpenAI=agent、ADK=runtime、LangGraph=state
③ 用「按瓶颈选」的判据选型：context 爆→Claude、流程要显式→LangGraph、多 agent 分工→handoff、跨框架统一→ADK

知识背景
四家 harness 都能跑 agent，也都能接入 MCP 等标准（A2A 等支持程度各家不一），但核心抽象不同。这个核心抽象叫 第一公民（first-class citizen，指一个框架里「其余一切都围着它转、处处可见可操作」的那个中心概念）。Claude Code 以 context 为第一公民、OpenAI Agents SDK 以 agent 为第一公民、Google ADK 以 runtime（event loop） 为第一公民、LangGraph 以 state 为第一公民。选不同的第一公民，决定了这家框架「擅长什么、别扭什么」。

上一课把「标准生态」交给 harness 落地。这一课回答：同样的标准，四家落地为什么不一样。

因为「agent 怎么编排」没有一个唯一答案，四家各挑了一样东西当中心。就像四家造车厂都遵循「四个轮子 + 一个方向盘」的通用标准，但一家把发动机当灵魂、一家把智能座舱当灵魂、一家把底盘当灵魂——车都造得出来，开起来完全不同。所以下面先看清「第一公民」这个根子。

第一种哲学：Claude Code 为什么把「context」（上下文窗口）当第一公民？它的一切设计是怎么围着「省 context」转的？
提示：有没有两件设计是专门为了「少往上下文里塞东西」的？它们各自怎么做到？
▾
知识背景
Claude Code（Anthropic 的编程/agent harness）是 context-first 的代表：它把 context（上下文窗口，模型这次推理能「看到」的全部 token，稀缺且昂贵）当成最该省的核心资源，一切设计围着它转。两件标志性设计都是省 context 的：subagent（子智能体，第 44 课——把中间过程隔离到独立窗口、只回结论）和 skill（第 46 课——渐进披露、描述常驻正文按需）。Anthropic 官方以「context 是稀缺资源」为主线串起 subagent / skill / hook（见其 context engineering 一文与 steering 博客）。

上一张引出「第一公民」四种选法。这一张展开第一种：context-first。

因为context 又贵又小，装多了会撑爆、会变慢。就像一张只有一平米的办公桌：你要在这上面干完所有活，就会拼命把暂时不用的东西塞进抽屉（subagent）、把常用流程写成一张小卡片贴在桌角而不是摊开整本手册（skill）。所以下面算它怎么「省 context」。

🧮 第二笔账：context-first 怎么省 context
Step 1：subagent 隔离中间过程（承 44 课）
方式主 context 占用
读 50 文件全塞主窗口50×500=25,000 token
subagent 只回结论500 token

信念推论

Claude Code 把 context 当第一公民——因为 context 又贵又小，所以一切设计都围着「省」转：subagent 把中间过程隔离走（省 24,500）、skill 把知识渐进披露（省 190,000）。代价是「流程不显式」：你没法像画流程图一样一眼看清整个编排——这正是后面 LangGraph 要反着来的地方。

知识背景
OpenAI Agents SDK（OpenAI 的 Python agent 框架）是 agent-first 的代表：它把 agent（一个带指令、工具、模型的独立工作者）当第一公民，一切围绕「让 agent 这个单位既独立又能协作」。两件标志性设计：handoff（交接——一个 agent 做完，把控制权连同一段上下文「接力」传给另一个 agent）和 guardrail（护栏——检查 agent 输入与最终输出的检查器，输入护栏默认与 agent 并行跑，出错就拦截）。官网将 handoff、guardrail 列为核心机制（另有 session、Runner、Tracing 等）。

上一张是 context-first。这一张展开第二种：agent-first。

因为有些任务天然要「分工」——一个 agent 管接单、一个管退换货、一个管技术咨询。就像接力赛：每个队员只管自己那一棒，跑到交接点把手里的棒（上下文）递给下一个，边上还有裁判（护栏）盯着谁犯规。所以下面算一次 handoff 的分工账。

交接物内容

🎯 关键认知

OpenAI 把 agent 当第一公民——因为多 agent 分工要「接力」，所以 handoff 传控制权+上下文（1 个 triage + 2 个专业 agent 无缝交接）；因为要防错，所以 guardrail 并行盯输入输出。代价是「流程难显式控」：handoff 是 agent 自己判断往哪交，编排散在每个 agent 里，不像一张流程图那样一眼可见。

第三种哲学：Google ADK 为什么把「runtime」（运行时）当第一公民？它靠什么把「LLM 驱动的 agent」和「确定性的工作流」统一成同一个东西来跑？
提示：想一想——一个是「让模型自己决定下一步」的 agent，一个是「写死的 if-else 流程」，这俩能共用同一个「发动机」吗？
▾
知识背景
Google ADK（Agent Development Kit，Google 开源的 code-first 多语言（Python/Java/Go/TypeScript 等）agent 框架）是 runtime-first 的代表：它把 runtime（运行时，统一驱动 agent 前进的「发动机」）当第一公民。核心机制是 event loop（事件循环，一个不断「取事件 → 处理 → 产生下一步」的循环）。ADK 的关键洞见：LLM agent 和确定性 workflow agent 不该是两套代码，而该被同一个 event loop 驱动——LLM agent 只是「下一步由模型决定」的事件，确定性 workflow 只是「下一步由代码决定」的事件。ADK 2.0 又在这个 runtime 上收敛了图式编排。

上一张是 agent-first。这一张展开第三种：runtime-first。

因为真实系统里，有的步骤要模型判断（「这封邮件要不要回」）、有的步骤是写死的（「金额 < 100 就放行」），两种逻辑混在一起最难维护。就像一台洗衣机：不管洗什么模式，滚筒都靠同一个电机转——ADK 的 event loop 就是那个统一的电机。所以下面看一个 event loop 怎么同时驱动两种 agent。

🧮 第四笔账：runtime-first 怎么统一两套逻辑
Step 1：两种 agent 各是什么
类型下一步谁定
LLM agent模型推理决定
workflow agent写死的代码决定
两种 agent 的「下一步」来源不同：一个是模型、一个是代码。
Step 2：event loop 统一驱动
环节动作
取事件拿到下一步该做什么
处理LLM 或代码执行
产生下一步再投回循环
event loop 只有 1 个循环：取事件 → 处理 → 产生下一步，两种 agent 都在这 1 个循环里跑。
Step 3：统一后的好处
统一前统一后
两套代码、两套调试1 套 runtime 通吃
边界处要手工拼无缝切换
统一 = 1 套 runtime 通吃 LLM 与 workflow，省掉两套代码的拼接。
🎯 关键认知

Google ADK 把 runtime 当第一公民——因为真实系统里「模型判断」和「写死逻辑」混在一起，所以它用 1 个 event loop 把 LLM agent 和确定性 workflow agent 统一驱动：取事件 → 处理 → 产生下一步。代价是「抽象偏底层」：你得先接受「一切都是事件循环」这套世界观，上手门槛比「直接定义 agent」高。

第四种哲学：LangGraph 为什么把「state」（状态）当第一公民？它靠什么让整个 agent 流程变成一张「一眼能看懂的图」？
提示：一个流程若能被画成流程图，需要哪几样零件？
▾
知识背景
LangGraph（LangChain 的图式编排框架）是 state-first 的代表：它把 state（状态，整个流程共享的、随时可读可写的显式数据结构）当第一公民。三个核心件：State（存所有中间结果）、Node（节点，一个步骤/函数）、Edge（边，决定下一步走哪个节点，可循环/分支/并行）。它的杀手锏是 checkpoint（检查点，把 state 的每个版本存下来），这让「人在环中」（human-in-the-loop，人可在任意步暂停、审阅、改 state 再继续）变得自然。官方文档把 checkpoint 列为 human-in-the-loop 与 resume 的前置。

上一张是 runtime-first。这一张展开第四种：state-first。

因为有些流程要「显式可控」——每一步走到哪、中间结果是什么、卡住了能不能从原地接着跑。就像一张画在纸上的流程图：每个框（节点）干一件事、每根箭头（边）指向下一步，走到哪、哪一步错了，一眼就知道；还能在任意一个框旁边停下来盖个章（checkpoint），下次从这接着走。所以下面看 state-first 怎么把流程变成「图」。

🧮 第五笔账：state-first 怎么把流程变成图
Step 1：三件核心各是什么
件作用
State存所有中间结果
Node一个步骤/函数
Edge决定下一步走哪个节点
State / Node / Edge 三件套 = 一张显式的流程图。
Step 2：Edge 支持哪几种走法
走法例子
循环不达标就回到上一步
分支按条件走 A 或 B
并行同时跑几个节点

Step 3：checkpoint 让人能在环中插手
有 checkpoint无 checkpoint
任意步暂停、审阅、改 state 再续只能从头跑

🎯 关键认知

LangGraph 把 state 当第一公民——因为流程要「显式可控」，所以 State 存所有中间结果、Node 拆步骤、Edge 决定下一步（可循环/分支/并行），checkpoint 把每个版本存下来让人能在任意步插手。代价是「样板代码多」：每一步都要显式写 state 怎么变、边怎么连，比「一句话定义 agent」啰嗦——这是它和 OpenAI 的 agent-first 正好相反的地方。
