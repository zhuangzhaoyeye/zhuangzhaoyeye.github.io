第 26 课：多智能体与协议

紧接上一课（第 25 课《规划与反思》）——那一课把"想清楚再动手"讲透了，这一课只追一个问题：把任务交给多个 Agent，究竟是变强了，还是只是变贵了？我们从"多智能体不一定更强"的实测讲起，把收益/成本账、A2A 的能力发现、通信拓扑与消息设计、上下文工程，一路算到最底层的三笔账——token、延迟与失败率。

🎯 学完这 6 步你将能够：
① 用 token 账说明"为什么不一定更强"：单 Agent 一次任务约 80,000 token、多智能体约 15× 普通对话 = 300,000 token，换来约 90.2% 的相对提升（relative lift，不等于提高 90.2 个百分点）
② 用 N(N−1)/2 算通信规模：5 个 Agent 网状要 10 条通道、中心辐射只要 4 条；协议把集成复杂度从 O(N²) 压到 O(N)
③ 用连乘算多 Agent 串联的失败率：单点 0.9 的 4 个 Agent 只剩 0.9⁴ ≈ 0.656；再用摘要 + 检索把上下文从 20,000 压到 5,000（降 75%）
🗺 本节推理链（6 步逻辑递进：从"多智能体不一定更强"到"账算清再挑框架"）
1要让 Agent 完成一个长任务而不是只回应一句，这就要求先问清：多个 agent 一起做，真的更强吗？它们各自持有 context 与 token 预算，得先摆上账。 多智能体先算收益账。
↓
2既然「多智能体先算收益账」，所以要先看任务能不能拆开——读多写少、线程独立才值得并行，要共享同一份 context 的任务则不然，否则协调成本会吃掉 token 红利。 拆得开才并行。
↓
3既然「拆得开才并行」，这就要求 Agents 之间先能相互发现——先有 AgentCard 说清"我是谁、我能做什么"，彼此的 context 与任务才有地方对接。 先有 AgentCard。
↓
4既然「先有 AgentCard」，所以接下来要定它们怎么说话——选通信拓扑、设计结构化 message，只在必要时交换彼此的 context 与 token，否则多个 agent 会各改一份、互相打架。 通信要有拓扑。
↓
5既然「通信要有拓扑」，这就把压力推到每条链累积的 context 与 token 上——越长的任务越紧，只能靠摘要、检索与外置状态把轨迹压进窗口。 上下文要工程化。
↓
6既然「上下文要工程化」，所以最后把三笔账合起来——token、延迟、失败率，算清"贵在哪"之后才会发现：LangGraph / AutoGen / CrewAI 这些框架替你做的，正是前面这五件事。 账算清再挑框架。

要让多个 Agent 协作真正划算，它的账单要怎么算？
提示：别急着下结论——先把"多几个人一起做"的收益，和它要花的 token 账单，放到同一个天平上看。
▾
知识背景
两天内出了两篇针锋相对的文章：2025-06-12，Cognition 先发《Don't Build Multi-Agents》，主张"不看清场景就别上多智能体"；次日 2025-06-13，Anthropic 发表《How we built our multi-agent research system》，用"主 Agent 派活、子 Agent 并行搜索"做深度研究——多智能体（Opus 4 作主 + Sonnet 4 作子）在内部研究评测上比单智能体 Opus 4 相对提升约 90.2%；报告同时写明——单个 Agent 约用普通对话的 4× token，多智能体约 15×。（两文后来更多被视为互补而非对立：一篇讲适用边界，一篇给可行架构。）

上一部分我们讲过"想一步、做一步"的循环能靠外部观察纠错。这一课换一个问题：把任务交给多个 Agent 一起做，是不是就一定更强？

因为多智能体的收益（并行、互相纠错）要用 token 去买，而 token 账单会成倍放大——所以"更强"必须放到账上比，不能凭感觉。就像点外卖凑满减：多凑几单看似更划算，多付的配送费却可能把折扣吃回去。

🧮 第一笔账：多智能体到底换来了什么
Step 1：收益和账单是同一次实验里的两个读数
指标单智能体多智能体（主 + 子）
内部研究评测基线相对提升约 90.2%
相对普通对话的 token约 4×约 15×
数据来源Anthropic《How we built our multi-agent research system》（2025）
结构说明：这份实测里，多智能体把成绩相对抬升了约 90.2%（relative lift，不是"提高 90.2 个百分点"），同时把 token 从约 4× 提到约 15×。两个读数出自同一份报告，不是本课估算。
Step 2：换算成能对账的 token 数
项数值
一次任务的普通对话量（示意）20,000 token
单 Agent ≈ 4× 普通对话4 × 20,000 = 80,000 token
多智能体 ≈ 15× 普通对话15 × 20,000 = 300,000 token
算术：以普通对话 20,000 token 为锚（示意），单 Agent 约 80,000、多智能体约 300,000；多智能体是单 Agent 的 300,000 ÷ 80,000 = 3.75 倍。
Step 3：多花的 token 与"相对提升"的关系
项数值
多智能体比单 Agent 多花300,000 − 80,000 = 220,000 token
内部评测相对提升约 90.2%（relative lift，非"90.2 个百分点"）
能否折算成"每 1% 花多少 token"不能：相对提升与百分点不是同一口径
算术：多花 220,000 token 换来的是约 90.2% 的相对提升（relative lift）——它不是"成功率提高 90.2 个百分点"，两者口径不同，不能直接相除得到"每 1% 的成本"。
🎯 关键认知

多智能体不是"更聪明的模型"，而是"允许花更多 token"的架构：Anthropic 自己分析发现，仅 token 用量一项就解释了 80% 的性能差异。先算账，再决定要不要上。

那什么时候该用多智能体、什么时候是自找麻烦？
提示：先别看模型能力，看任务结构——子任务之间要不要共享同一份东西？能拆开的才谈得上并行。
▾
知识背景
CooperBench（Khatua 等，arXiv:2601.13295，斯坦福与 SAP 实验室，2026）让两个 Agent 在同一份代码里各改一个功能：单 Agent 独做时成功率约 50%，两个 Agent 协作时掉到约 25%（这是最强模型 GPT-5 / Claude Sonnet 4.5 一档的结果；论文全模型口径为平均下降约 30%），作者称之为"协调的诅咒"。Anthropic 也明确：需要所有 Agent 共享同一份 context、或彼此强依赖的任务，不适合今天的多智能体。

上一张卡片算清了多智能体的收益与账单。那么，什么任务该上、什么任务别上？

因为多智能体只在"任务能切成互不依赖的并行子任务"时才划算；一旦子任务要共享同一份上下文、互相依赖，协调成本（多出来的 token 与等待时间）就会盖过并行收益。就像装修：砌墙和铺砖互不干扰，可以两队并进；水电和墙面必须分先后，硬拆成两队只会互相等。所以先看任务结构，再决定拆不拆。

🧮 第二笔账：拆得开才并行
Step 1：任务形状决定值不值得
任务形状适合多智能体为什么
广度研究（多来源、互不依赖）是线程独立，信息超一个窗口
同标准对比多个对象是每个对比独立跑、结果可合流
多个 Agent 改同一份代码否要共享上下文，改动互相冲突
串行流水线否没有可并行的部分
强延迟敏感否编排每波都要等最慢的 worker
结构说明：判据是"子任务之间要不要共享同一份状态"——不共享才谈得上并行。
Step 2：并行能快多少（示意）
项数值
4 个独立子任务，每个 10 秒串行 4 × 10 = 40 秒
并行后关键路径最慢子任务 10 秒 + 合并 2 秒 = 12 秒
加速比40 ÷ 12 ≈ 3.33 倍
算术：4 个独立子任务（示意）每个 10 秒，串行 40 秒；并行后关键路径 = 最慢那条线程 10 秒 + 合并 2 秒 = 12 秒，加速约 3.33 倍。加速比的上限由最慢的线程决定，不由子任务个数决定。
Step 3：反过来，协调成本也会吃掉收益
情形观察
两个 Agent 改同一份共享代码成功率约 50% → 25%（CooperBench，2026；最强模型档）
必须共享同一份上下文Anthropic：这类任务不适合今天的多智能体
只是"多采样几次"与直接多采无本质区别，白付协调费
算术：共享写场景下成功率从约 50% 掉到约 25%（约砍半）——这是最强模型 GPT-5 / Claude Sonnet 4.5 一档的结果，论文全模型口径平均下降约 30%。一句话判据：读多写少、线程独立 → 值得并行；写共享状态、强依赖 → 保持单线程。
🎯 关键认知

判据是任务结构：能切成独立、读多写少的线程，才上多智能体；子任务要共享同一份状态时，一个带规划的 Agent 往往更省更稳——并行省下的时间，要拿多出来的 token 去换。

两个 Agent 要协作，为什么必须先解决「我是谁、我能做什么」？
提示：想一次"把活派给别人"的完整过程——你得先知道对方的身份和能力，否则派出去会发生什么？
▾
知识背景
A2A（Agent2Agent，Google 于 2025-04-09 发布，50+ 家厂商参与）是 Agent 之间的互操作协议：用 AgentCard 描述身份与能力，用 Task / Message / Artifact 交换任务与产物。官方把"能力发现"列为协议的第一项能力，并指出没有统一协议时，两两对接的集成成本按 O(N²) 增长。

上一张卡片说明要挑能拆开的任务。那拆完之后，两个 Agent 凭什么才能相互派活？

因为派活的前提是"可发现"与"可验证"：不知道对方能做什么就会派错活，不知道对方是谁就无法验证结果、也可能被冒名者接走。就像进公司找人办事：先看工牌（身份）和岗位（能力），再谈具体做什么，否则会把报销单交给实习生。所以协议要先解决"我是谁、我能做什么"。

🧮 第三笔账：能力发现与它的规模效应
Step 1：A2A 的四类核心对象
对象作用
AgentCard（智能体名片）身份 + 能力清单，放在 /.well-known/agent-card.json（旧版曾用 agent.json）
Task（任务）一次可跟踪、可回访的委派
Message / Part（消息 / 片段）对话消息与其中的内容片段
Artifact（工件）任务产物
结构说明：先在名片里完成"发现"（AgentCard），再派单（Task）、靠消息推进（Message）、用产物收尾（Artifact）。
Step 2：没有协议时，通道数按 O(N²) 涨
Agent 数 N两两直连 N(N−1)/2有统一协议后
33 × 2 ÷ 2 = 33
55 × 4 ÷ 2 = 105
1010 × 9 ÷ 2 = 4510
算术：5 个 Agent 两两直连要 10 条通道、10 个要 45 条；有统一协议后，每个 Agent 只对自己的一张名片负责、彼此通过名片对接，描述复杂度降为 O(N)，因此通道数降回 N。协议把集成复杂度从 O(N²) 压到 O(N)——链上流动的其实是彼此的 context 与身份。
Step 3：AgentCard 里写什么
字段内容
身份与描述我是谁、做什么
服务端点到哪里找我
鉴权要求怎么安全连接
能力（capabilities）是否支持流式、推送
技能（skills）我能接哪些活
结构说明：名片里"能力"与"鉴权"必须同时有——只写能力、不写鉴权，等于把门敞开。
🎯 关键认知

协议解决两件事："能否互通"（发现与格式）与"敢不敢互通"（身份与权限）。AgentCard 是两件事的交汇点——它既是接线图，也是准入门槛。

分好角色之后，它们凭什么才能不互相打架？
提示：先想"消息走哪条路、谁负责收口"，再想"每次消息里到底该放全文，还是放个指针"。
▾
知识背景
Anthropic 的编排者—工作者（orchestrator-worker）模式里，主 Agent 把任务与共享状态写进外部存储，子 Agent 各自在独立 context 里跑，结果写回文件系统、只把轻量引用回传编排者，而不是把全文塞进对话。这决定了通信既要解决"拓扑"问题，也要解决"消息放什么"的问题。

上一张卡片用 AgentCard 解决了"我是谁、我能做什么"。可角色分好之后，消息怎么走才不会互相打架？

因为通信拓扑（谁和谁连、消息怎么走）决定了"谁在等谁、谁和谁冲突"：中心辐射只有一个编排者收口，谁来合流很清楚；网状人人对话则容易两两改同一件事而打架。就像开会：主持人一个人收口，比分头两两私聊更容易达成一致。所以先定拓扑，再定消息里放什么。

🧮 第四笔账：拓扑选谁、消息放什么
Step 1：三种通信拓扑对比
拓扑通道数（N 个 Agent）优点风险
中心辐射（orchestrator-worker）N − 1好合流、易追踪中心是单点
网状（peer-to-peer）N(N−1)/2无单点易冲突、难追踪
黑板（shared state）各写同一存储解耦要并发控制
算术：5 个 Agent 时，中心辐射 5 − 1 = 4 条通道、网状 5 × 4 ÷ 2 = 10 条。通道越多，追踪与冲突的成本越高。
Step 2：消息传"全文"还是传"引用"
做法每次传递5 个子产物合计（示意）
传全文5,000 token5 × 5,000 = 25,000 token
传引用（指针 + 摘要）100 token5 × 100 = 500 token
省下1 − 500 ÷ 25,000 = 98%
算术：子产物（示意）每个 5,000 token，若把全文塞进每次消息，5 个就是 25,000；改成"写进外部存储、只传引用和摘要"，只花 500，省 98%。这正是 Anthropic 的做法。
Step 3：一条消息该带什么
字段作用
任务 id同一件事的多次消息可归并
发送方 / 接收方谁问谁、防串台
意图派单 / 汇报 / 追问 / 收尾
产物引用指向外部存储，不塞全文
状态进行中 / 需要输入 / 完成
结构说明：消息是"结构化信封"而非聊天记录——带上任务 id 与状态，编排者才能在多线程里分清谁在汇报哪件事。
🎯 关键认知

拓扑的判据是"写操作是否单线程"：多个 Agent 只读、只有一个编排者合流就稳；多个 Agent 同时写共享状态就容易打架。消息则要"传引用不传全文"。

5
长任务跑到一半，上下文窗口塞满了怎么办？
提示：想一想"能不能少带一点"——哪些信息是这一步真正要看的，哪些可以先收起来、要用再取？
▾
知识背景
上下文工程（context engineering）指的不是"写更好的提示词"，而是决定每一步把哪些 token 放进有限的上下文窗口。长轨迹会随步数线性增长，所以必须靠摘要、检索与外置状态来压缩——这和上一部分的记忆与检索工程是同一条线。

上一张卡片把通信拓扑和消息格式定了下来。可长任务跑到一半，上下文窗口塞满了怎么办？

因为轨迹会随步数线性增长，每多一步就多一段要带上，20 步就要占掉 128K 窗口的约 31%，很快逼近需要压缩的区间；硬塞只会让模型对中段信息的利用更差。就像出差装箱：不是把所有家当都带上，而是按行程挑必需品、其余寄存，要用再取。所以先算清轨迹怎么长，再看三种压缩各管什么。

最省事的做法是「窗口还能装就继续装」；但轨迹按步数线性长，每步 2,000 token，20 步就是 40,000，占 128K 窗口约 31%（与第 22 课同一窗口口径），继续下去很快逼近上限，而且模型对上下文中间部分的利用最差。所以长任务必须主动做上下文工程，而不是等它自己塞满。

🧮 第五笔账：把长轨迹压进窗口
Step 1：原始轨迹按步数线性增长
项数值
每步轨迹（示意）2,000 token
10 步10 × 2,000 = 20,000 token
20 步20 × 2,000 = 40,000 token（占 128K 窗口约 31%）
算术：每步 2,000 token（示意），10 步 20,000、20 步 40,000——20 步已占 128K 窗口的约 31%（与第 22 课同一窗口口径），不压缩的话，任务越长窗口越紧，很快逼近上限。
Step 2：三种压缩手段各管什么
手段做法代价 / 风险
摘要（compaction）把历史压成要点信息有损
检索按需取回相关片段可能漏召
外置状态文件 / 数据库存全量多一层读写
分工：摘要管"方向"、检索管"细节"、外置状态管"全量"——三者配合，才能在有限窗口里长期运行。
Step 3：压缩后能省多少（示意）
方案进上下文窗口的量
不压缩20,000 token
摘要 2,000 + 按需检索 3,0002,000 + 3,000 = 5,000 token
降幅1 − 5,000 ÷ 20,000 = 75%
算术：摘要到 2,000、按需检索 3,000，进窗口从 20,000 降到 5,000，降幅 75%（示意）。判据不是"能塞多少塞多少"，而是"这一步真的需要看到哪些 token"。
🎯 关键认知

上下文工程不是"写更好的提示"，而是决定每一步把哪些 token 放进窗口：摘要给方向、检索给细节、外置状态兜住全量。这是多智能体能不能跑长大的最后一道工程约束。

6
多智能体到底贵在哪——为什么本课不教框架？
提示：把账拆成三笔分开算——多花了多少 token、编排要等多慢、串联起来失败率怎么变；再想框架替你做的到底是什么。
▾
知识背景
LangGraph / AutoGen / CrewAI 是常见的多智能体框架，它们把"能力发现、任务委派、通信拓扑、消息格式、上下文压缩"固化成现成的壳。但 Anthropic 的实测提醒：这些机制背后是真实的代价——多智能体约 15× 普通对话的 token，编排者每波都要等最慢的 worker，而多个 Agent 串联会让整体失败率连乘上升。

上一张卡片把长轨迹压进了窗口。最后把三笔账合起来看，并回答一个绕不开的问题：为什么本课不教任何具体框架？

因为多智能体的代价分布在三处——token、延迟与失败率；而框架替你做的，正是前面五张卡片讲的事。就像学开车：先懂油门、刹车和路况判断，再挑哪款车，否则换个车型就不会开。所以先把三笔账算清，再谈工具。

🧮 第六笔账：token、延迟、失败率
Step 1：token 账
口径倍数（相对普通对话）一次任务（示意）
普通对话1×20,000 token
单 Agent约 4×80,000 token
多智能体约 15×300,000 token
算术：多智能体是单 Agent 的 300,000 ÷ 80,000 = 3.75 倍（倍数由本课以 20,000 token 示意锚点推算；约 4× / 15× 才是 Anthropic 口径）。
Step 2：延迟账
做法总时长（示意）
串行 4 步，每步 5 秒4 × 5 = 20 秒
编排 + 4 个 worker 并行 + 合并 2 秒5 + 2 = 7 秒
多波次任务每波都要等最慢的 worker
算术：并行把 20 秒压到 7 秒；但编排者每一波都阻塞在最慢的 worker 上——只要一个 worker 卡住，整波都等它，这是延迟的尾部风险。
Step 3：失败率账
Agent 串联数单点成功率 0.9单点成功率 0.99
40.9⁴ ≈ 0.6560.99⁴ ≈ 0.961
100.9¹⁰ ≈ 0.3490.99¹⁰ ≈ 0.904
算术：多个 Agent 串起来，整体成功率是各自成功率的连乘——0.9 的 4 个串联只剩 0.656、10 个只剩 0.349。并行能省时间，但串联步骤越多、整体失败率越高，这与上一部分"步数越多越容易崩"是同一条规律。

那为什么本课不教 LangGraph / AutoGen / CrewAI 这些框架？因为课程立场是先懂原理：框架替你做的，正是这 6 张卡讲的 6 件事——能力发现（AgentCard）、任务委派、通信拓扑、消息设计、上下文压缩、成本与失败率的账。等你清楚它们内部在干什么，用任何框架都只是 API 问题；反过来，只会调框架的人，一旦出问题就不知道该改拓扑还是改消息格式。

🎯 关键认知

收口：多智能体的完整链条是——先算收益账（不一定更强）→ 挑能拆开的任务 → 用 AgentCard 解决"我是谁" → 定通信拓扑与消息格式 → 做上下文工程把轨迹压进窗口 → 三笔账（token / 延迟 / 失败率）都算清。框架只是把这些固化下来的壳——先懂原理，再挑工具。
