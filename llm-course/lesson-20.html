第 20 课：提示工程

上一课我们学会了怎么「证明」一个模型变好了——用评测把分数拆成构念、污染、判官与噪声。这一课回到最日常、也最像玄学的动作：把话说给模型听。同一个模型、同一个问题，只是换个问法，结果为什么能差一大截？提示里给不给例子（zero-shot 零样本 / few-shot 少样本，即给 0 个还是几个示例）、要不要让它先一步步想（Chain-of-Thought 思维链）、输出怎么卡成 JSON（用键值对表示数据的文本格式）、调不好时该改提示还是改检索与微调、一个 Agent 的 prompt（提示词）到底由哪几块拼成——这一课把「提示工程」从手感变成可算的动作，也为下一课《从 Prompt 到 Agent》把最基础的接口讲清楚。

🎯 学完这 6 步你将能够：
① 用同一个模型的两个候选分数算清「换个问法」动了什么——logits（模型给每个候选 token 打出的原始分数）只挪 0.2，Top-1 就可能翻转（softmax(2.1, 2.0) 从 0.525/0.475 变成 0.4256/0.5744）
② 用 TriviaQA 的三个读数（64.3 / 68.0 / 71.2）算清 zero-shot→few-shot 的收益与 token 成本（给 5 个例子，prompt 膨胀 8.5 倍），并用 Binomial(40, 0.569) 算出「多条理由投票」把正确率抬到 76.56%
③ 用 8000 token 的窗口把 Agent 的 prompt 拆成 system prompt（系统提示）+ 角色 + context（上下文），并算出历史涨到 6000 token 时超支 400 token

▾
知识背景
你把整段发给模型的输入就叫 prompt（提示词）；专门琢磨怎么把它写好，就是 prompt engineering（提示工程）——不改模型的一个权重，只改你输入的文字。ICLR 2024 的《Quantifying Language Models' Sensitivity to Spurious Features in Prompt Design》（Sclar 等，arXiv:2310.11324）系统证明：只把标点、空格、分隔符换一换（含义完全不变），很多开源模型的分数就会大幅波动。NVIDIA 的 SCORE 评测（arXiv:2503.00137）也测到：仅仅把 MMLU-Pro 的题目换一种说法，准确率波动可达 10%。这说明 prompt 不是「随手写的说明」，而是模型这次作答的条件。

先澄清一个直觉误区：模型不是「听懂了你的意思」，而是「在你给的条件上，接着往下续写」。

因为它每一步输出，都是从一张候选表里挑一个 token——而这张候选表（每个候选的分数叫 logits（模型给每个候选 token 打出的原始分数））完全由你这段 prompt 决定。prompt 里多一个词、少一个标点，候选表就会挪一挪。

就像同一份外卖备注：写「不要辣」和写「少放辣椒、小孩吃」，厨师出餐很可能就是两道菜——你改的是备注，不是厨房。回到术语：能左右模型输出的这段输入，就是 prompt。所以下面用三笔账，把「换个问法」到底动了什么算出来。

🎯 关键认知

知识背景
GPT-3 论文《Language Models are Few-Shot Learners》（Brown 等，arXiv:2005.14165，2020）提出了 in-context learning（上下文学习）：把任务说明和几个示例写进输入，模型不做任何梯度更新，就能完成没专门训练过的任务。按输入里放几个示例，分三档——zero-shot（零样本，一个例子都不给）、one-shot（单样本，给 1 个）、few-shot（少样本，给若干）。论文用 175B 参数的 GPT-3 在 TriviaQA 上报告了三个读数：64.3% / 68.0% / 71.2%。

上一张卡片看清了 prompt 是「条件」。这一张问：条件里放几个例子，为什么效果差这么多？

因为模型读这几个例子时，参数一个都没变——它只是把例子当成了本轮 context（模型这一次能看到的全部输入）的一部分，在续写时照着格式与规律往下接。就像你临时给同事看三张填好的报销单：他没参加过培训、也没改自己的习惯，却照着样例把第四张填对了——他「会」的是当场照猫画虎，不是学会了新技能。这类「不改参数、只靠上下文里的例子当场学会」的能力，就叫 in-context learning。所以下面用 GPT-3 论文的三个真实读数，把「给例子」的收益和代价一起算。

更自然的做法是一个例子都不给（zero-shot）——模型只能靠指令本身去猜格式；GPT-3 在 TriviaQA 上从 zero-shot 的 64.3% 抬到 few-shot 的 71.2%，这 6.9 分就是「当场照抄示例格式」换来的。

🎯 关键认知

为什么让它「先一步步想、再回答」就对了？
提示：数一数模型为这道题「多花了多少步计算」，再想这些步骤是你改提示就能加上的，还是必须训练才有。
▾
知识背景
Chain-of-Thought（思维链，简称 CoT）出自 Wei 等《Chain-of-Thought Prompting Elicits Reasoning in Large Language Models》（arXiv:2201.11903，NeurIPS 2022）：只要在示例里把答案换成「带中间推理步骤」的版本，模型就会跟着分步推理。论文用 PaLM 540B 在数学应用题 GSM8K 上报告 17.9% → 56.9% 的提升。在此之上，Wang 等《Self-Consistency Improves Chain of Thought Reasoning in Language Models》（arXiv:2203.11171，ICLR 2023）又提出 Self-Consistency（自洽投票）：采样多条不同的推理链，对最终答案投票，取最一致的那个。

上一张卡片给的是「例子」。这一张问：对同样的题目，为什么让它先写推理步骤、再给答案，正确率就上去了？

因为模型每多吐一个 token（它输出的最小文本单位）就多做一步计算——直接答只能一口气算完，先想再答等于把计算量摊开。就像让心算和列竖式比：题目不会变，但列了竖式就有草稿可对齐、可回看。这种做法叫 Chain-of-Thought。要特别划清一条线：CoT 是「推理时」的技巧——你改的是提示，模型权重一点没动；而「把推理能力直接训进权重」是另一条路，那是第 12 课（推理模型与 RLVR（用可验证的奖励把推理写进权重））的主题。所以下面把 CoT 的收益、代价，以及它的升级版 Self-Consistency 一起算。

更自然的做法是直接要答案——PaLM 540B 在 GSM8K 上直接答只有 17.9%，换成带步骤的示例后跳到 56.9%，这 39 分的差距全来自「把中间步骤也吐成 token」。

算术：Self-Consistency 让模型用较高 temperature（采样温度，越高越发散）采样出多条不同的推理链，再对最终答案投票。若单条正确率 p = 0.569、采样 n = 40，则多数票正确的概率 = Σ(k=21..40) C(40, k) × 0.569^k × 0.431^(40−k) ≈ 0.7656，比单条的 0.569 高出约 20 个百分点。论文实测（arXiv:2203.11171）在 GSM8K 上把思维链再提升 17.9 个百分点（即从该论文自己的贪心 CoT 基线 56.5% 绝对提升到约 74.4%；与本卡 Step 1 引 CoT 论文的 56.9% 略差，属两篇口径不同），SVAMP +11.0 个百分点、AQuA +12.2 个百分点、StrategyQA +6.4 个百分点、ARC-c +3.9 个百分点。
🎯 关键认知

思维链把「一口气算」摊成多步，Self-Consistency 再把「一条链」变成「多条链投票」。两者的共同点是都在推理时发生，权重不变——这和第 12 课「把推理能力训进权重」是两条不同的路。记住这条界线：提示层面的技巧，改的是 context；训练层面的能力，改的是参数。

怎样才能稳定拿到可被程序解析的 JSON，而不只是写一句「请输出 JSON」？
提示：想一下「生成」是逐 token 挑的——如果每一步都可能是任何一个字，你怎么保证最后拼出来的一定合法？
▾
知识背景
早期做法是 JSON mode：只保证输出「是一段合法 JSON」，不保证符合你要的字段。Structured Outputs（结构化输出）进一步：把 JSON Schema（一份描述数据结构的声明）随请求一起发给模型，约束解码只能生成符合该结构的 token。OpenAI 官方文档《Structured outputs》明确对比了两者：JSON mode「保证是合法 JSON，但不能保证严格符合所提供的 Schema」；结构化输出则推荐用于函数调用、结构化抽取与多步工作流（platform.openai.com/docs/guides/structured-outputs）。

上一张卡片的思维链会吐出一大段自然语言。这一张问：当下游是一个程序时，怎么保证它收到的一定是能解析的结构？

因为模型的输出是逐 token 采样出来的，每个位置都可能冒出任何字符——哪怕提示里写了「只输出 JSON」（JSON（用键值对表示数据的文本格式）），它也可能多一句「好的，这是结果：」，或漏掉一个括号，让整段解析失败。就像你要求实习生「只填表格」，他仍可能交回一张边角写了备注的纸——格式约束不能只靠口头叮嘱。所以行业给了两级做法：先是 JSON mode，再是 Structured Outputs。下面把「靠解析兜底」和「结构约束」的代价算出来。

更自然的做法是在提示里补一句「请只输出 JSON」——但生成是逐 token 采样的，模型仍可能多一句前缀或漏一个括号：示意算例里 15% 的输出格式不对，等于每次成功要多打约 1.176 次请求。

🧮 第四笔账：让输出「可被程序接住」要花多少
Step 1：自由文本 + 正则解析的返工率
项数值
单次调用解析失败率（示意）15%
成功率1 − 0.15 = 85%
每次成功平均需要的调用次数1 ÷ 0.85 = 1.176 次
1000 次成功实际要调用1000 ÷ 0.85 ≈ 1176 次
算术：若 15% 的输出格式不对、需要重试，那么「平均一次成功」要打 1 ÷ 0.85 ≈ 1.176 次请求；要拿到 1000 次可用结果，实际发出约 1176 次，多花 17.6%。口径：15% 为示意值（随任务与提示质量变化），算式展示返工率如何变成额外成本。
Step 2：用结构化输出把「格式正确」变成硬约束
项自由文本 + 正则结构化输出
格式合法率85%（示意）接近 100%
要不要写正则兜底要不用（按 Schema 反序列化）
缺字段风险有由 Schema 的必填字段声明挡住
说明（非算术）：结构化输出把「字段必须有哪些、是什么类型」写成 JSON Schema，随请求一起发给模型（platform.openai.com/docs/guides/structured-outputs）。它与 JSON mode 的区别是：JSON mode 只保证「是合法 JSON」，结构化输出还保证「符合你给的 Schema」。
Step 3：结构化输出还帮你省了什么
项数值
用结构化输出后解析失败率≈ 0
每次成功调用次数1.0 次
比 Step 1 的 1.176 次省下(1.176 − 1.0) ÷ 1.176 ≈ 15%
1000 次成功省下的调用约 176 次
算术：解析失败率压到接近 0 后，1000 次成功只需 1000 次调用，比自由文本的 1176 次少约 176 次（省 15% 的请求）。再加一层：把 temperature（采样温度，0 表示总取最大）设为 0，只去掉采样随机性、让同输入更趋同输出，但仍可能受批处理与浮点非确定性影响，不能承诺逐字可复现。
🎯 关键认知

让输出「可被程序接住」有三层，缺一层都不稳：① 说清要什么结构（提示里给 Schema）→ ② 用结构约束解码（结构化输出，把非法 token 从候选里挡掉）→ ③ 关掉随机性（temperature = 0）。这三层做完，「解析输出」才从「每次写正则兜底」变成「直接反序列化」。这也是第 22 课「工具调用」的地基：要调用工具，先得稳定拿到工具名和参数。

5
提示词怎么写都调不好时，该继续改提示，还是该去改检索 / 微调？
提示：先分清模型「不知道」和「不会做」——没见过的事实，调提示没用；不熟练的动作，才可能靠数据固化。
▾
知识背景
优化一个 LLM 应用有三条路，成本差一个量级：改提示（只改输入，零训练）、检索增强生成（RAG，检索增强生成：先从外部知识库检索相关文档，再塞进 context 让模型据此作答）、微调（用一批标注数据继续训练，改动模型权重）。RAG 由 Lewis 等《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》（arXiv:2005.11401，NeurIPS 2020）提出，专治「模型没记住的事实」。

上一张卡片让输出稳定了。这一张处理最现实的岔路：提示改到怀疑人生，是不是该换武器了？（承第 17 课 Card 6：那里从"选哪条路"入场，这里从"提示的边界"入场——两处侧重不同。）

因为三条路的病根不同：提示只能改 context（这次输入里有什么），改不了模型没见过的事实；检索能把外部文档塞进 context，却改不了模型「不擅长某动作」；微调才动参数，能把风格与格式固化进权重。就像孩子考试：题目没见过 → 给他翻书（检索）；粗心算错 → 多练题型（微调）；只是没看清题干 → 重读一遍题干（改提示）——用错药都白费。判断标准很简单：「不知道」找检索，「不熟练」才考虑微调，「没说清」先好好写提示。所以下面用成本把三条路摆到同一口径上。

更自然的反应是「调不好就继续改提示」——但如果病根是模型没见过某条事实，改多少次措辞都补不进这条知识；这时该把资料检索进来（RAG），而不是在提示上继续打磨。

现在把零件装起来：一个 Agent 的 prompt 到底由哪几块拼成，为什么不能只是一句「你是个助手」？
提示：数一数一个 Agent 一次循环里，除了你的问题，还有哪些东西必须被塞进去；再把它们的 token 加总，看看窗口装不装得下。
▾
知识背景
聊天接口把一次请求拆成几条带角色（role）的消息：system（系统角色，放角色设定与规则）、user（用户角色，放本轮问题）、assistant（助手角色，放模型上一轮的回答）。开头那段固定的 system 消息就叫 system prompt（系统提示）。在 Agent 里，每一轮还要把工具说明、长期记忆、历史对话和外部检索结果一起拼进 context——这套「把什么、以什么顺序、放多少」的动作，就是 上下文组装。

上一张卡片给定了一条选型线。这一张把整课的零件装起来：一个 Agent 的 prompt 到底由哪几块组成？

因为Agent 不会被只喂一句问题，它每一轮都要把「我是谁、有什么工具、记得什么、刚才发生了什么、现在要干嘛」一起递进去——这些拼起来就是它这一轮的 context。其中固定不变的那部分叫 system prompt，会变的（历史对话、检索结果、工具返回值）再逐轮拼上。就像给新员工的工牌背面：先印死「你是谁、能开哪些门」，每天再贴上当天任务便签——工牌是常量，便签是变量。把这层想清楚，「prompt 工程」就升级成了上下文组装。所以下面用 token 预算把这四块算一遍，看看什么时候会撑爆窗口。

🎯 关键认知

Agent 的 prompt = system prompt（常量）+ 角色 + 动态 context（历史 / 记忆 / 检索 / 工具返回），而它天生受 token 预算约束。所以「会写 prompt」在 Agent 里变成了「会做上下文组装」：谁的优先级高、什么时候压缩、什么时候丢弃，都是可算的工程决策。带着这套组装方式，下一课《从 Prompt 到 Agent》就能进入真正的循环：让模型不只是回答一次，而是一边行动、一边把结果拼回 context。
