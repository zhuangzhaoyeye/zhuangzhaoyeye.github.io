第 46 课：Skill 技能

紧接第 45 课《Rule 规则》：那一课把「什么不能变」从模型手里拿走、交给确定性代码。这一课追它的对偶问题——「怎么做」这件能变、但要做得对的事，怎么沉淀下来反复复用，而不是每次重写 prompt？ 我们从「工具只能执行函数、带不了程序性知识」讲起，把 skill（技能，知识打包单元）拆成 SKILL.md 的结构与「渐进披露」省 context 的账，一路讲到它已经变成开放标准（70+ 平台、100 万个 skill），最后收口：skill 把「怎么做」从一次性 prompt 变成可复用、可移植的知识。

🎯 学完这 6 步你将能够：
① 说清工具（tool）与 skill 的分工：tool 是「连接层」（执行一个函数）、skill 是「知识层」（存「怎么做」的流程）
② 用「渐进披露」算出省多少 context：100 个 skill 只加载描述 ≈ 10,000 token，全加载正文 ≈ 200,000 token
③ 讲清 Agent Skills 已是开放标准（2025-12 发布、2026-10-22 捐给 AAIF、70+ 平台、100 万 skill），并分清 skill 与 subagent 的边界
🗺 本节推理链（6 步逻辑递进：从「怎么做怎么复用」到「标准生态」）
1要让 agent 每次都能「按同一套正确做法」完成一件反复出现的事，就必须把「怎么做」沉淀成可复用单元；而工具（MCP tool）只能执行一个函数、带不了「先做什么再做什么」的程序性知识，所以需要一个知识打包单元 skill。
↓
2既然「知识打包单元 skill」要把「怎么做」存下来，所以要看它长什么样——SKILL.md（YAML 描述 + 正文流程）加可选脚本/资源；描述先加载、正文按需加载（渐进披露）。
↓
3既然「渐进披露」让 skill 能省 context、装下几十个，而「复用」要跨工具才有意义，所以要看它是不是只有 Claude 自己用——Agent Skills 已是开放标准（2025-12 发布、2026-10-22 捐给 AAIF、70+ 平台）。
↓
4既然「开放标准」让 skill 能跨工具复用，所以要用好它，就得先界定它管的是哪一层——连接层 vs 知识层：tool 连到函数、skill 存「怎么做」。
↓
5既然「连接层 vs 知识层」把 skill 从 tool 里摘了出来，所以它还要和另一个「也能干子任务」的 subagent 划界——复用固定流程用 skill、隔离中间过程用 subagent（skill vs subagent）。
↓
6既然「skill vs subagent」划清了，所以收口——skill 让「怎么做」可复用、可移植；下一步看它和 MCP / A2A 一起构成的标准生态。

1
要让 agent 每次都用同一套「怎么做」完成一件反复出现的任务，光靠工具（MCP tool）执行函数够吗？不够的话，那套程序性知识该往哪里放？
提示：想一想「部署一次服务」要几步——拉代码、跑测试、构建、上线。工具能帮你执行其中某一步吗？还是它只会执行「一个函数」？
▾
知识背景
tool（工具，如第 23 课讲的 MCP tool，一个接受参数、执行函数、返回结果的函数）只能「执行」，带不了程序性知识（procedural knowledge，即「先做什么、再做什么、遇到什么情况怎么办」的流程）。skill（技能，一个含 SKILL.md 的文件夹，教 agent 某件具体任务的流程，可附带脚本与参考资料）要解决的正是「怎么做」这件事——Anthropic 官方明说：Claude Code 擅长通用知识工作，但常缺「真实业务任务需要的程序性知识」，于是发明了 skill（anthropic.com 捐赠公告原文）。

上一课把「什么不能变」交给 rule。这一课问它的对偶：「怎么做」这件能变、但要做得对的事，怎么复用。

因为工具只执行一个函数，带不了流程。就像一台只会「按一下做一道工序」的机器：它能焊一个点，但不知道「先焊哪、再装哪」的整套流程——流程要写在别处。所以下面算一笔「流程知识 vs 函数执行」的账。

🧮 第一笔账：工具执行函数 vs 流程知识
Step 1：一个「部署」任务有几步流程
步骤是「函数」还是「知识」
拉代码函数（工具能执行）
跑测试函数
构建函数
先测后部署的顺序流程知识（工具带不了）
部署 = 3 个函数 + 1 条「顺序与判断」的流程知识；工具只能做前 3 个，最后一条无处可放。
Step 2：把流程写成 prompt 每次重写，成本多高
项数值（示意）
部署流程 prompt300 token
一年做 100 次300 × 100 = 30,000 token
算术：每次重写 300 token 的流程，100 次就是 30,000 token，而且每次还可能写走样。
Step 3：沉淀成 skill 后，加载多少
方式每次成本
每次重写 prompt300 token
skill 只预载描述≈ 100 token
skill 不用时只预载一段约 100 token 的描述；真到部署那次，正文（流程本身）仍要加载——它省的是「每次重写、每次走样」，以及不做部署时的常驻成本。
🎯 关键认知

工具解决「能不能执行」，skill 解决「会不会做」——没有 skill，「怎么做」每次都靠重写 prompt（100 次 = 30,000 token、还易走样）；有 skill，它被沉淀成可复用单元，平时只占约 100 token 的描述。这正是「知识层」与「连接层」的第一次分野。

知识背景
一个 skill 就是一个含 SKILL.md 的文件夹，可能再附脚本、参考文档。SKILL.md 以 YAML frontmatter 开头，必需字段是 name（名字）和 description（一句话描述何时用）。渐进披露（progressive disclosure，把信息分层加载：启动时只预载 name+description，正文等 skill 被触发时才读）是它省 context 的关键——微软官方文档把 Skill 的加载分成「Advertise ≈100 token → Load <5000 token」等阶段（learn.microsoft.com）；Anthropic 官方文档与 agentskills.io 规范给的量级相同（元数据约 100 token/个、正文建议 <5k token），本卡手算走查用示意值 100 / 2,000 token（落在该区间内）、已注明。

上一张看到 skill 是「怎么做」的容器。这一张拆开它的结构，并算「渐进披露」省多少。

因为 context 是稀缺资源，不能把每个 skill 的全文都堆进去。就像书架上的书：你只把「书名 + 一句话简介」贴墙上，需要哪本再抽哪本出来读，而不是把 100 本书全摊在桌上。所以下面算这笔 context 账。

🧮 第二笔账：渐进披露省多少 context
Step 1：skill 的结构一张表
部分内容何时加载
name + description名字 + 一句话用途启动就载
body（正文流程）怎么做触发时载
scripts / 资源可选脚本/文档需要时载
只有 name+description 常驻，正文和脚本按需加载——这就是「渐进披露」的三层。
Step 2：100 个 skill 的 context 账
方式算式占用（示意）
只载描述100 × 10010,000 token
全载正文100 × 2,000200,000 token
算术：每个描述 ≈100 token、正文 ≈2,000 token；100 个 skill 只载描述占 10,000，全载正文要 200,000。
Step 3：触发后只加载 1 个正文
情形额外加载
触发 1 个 skill+2,000 token（只这 1 个正文）
其余 99 个0（仍只占描述）
用哪个才加载哪个的正文，剩下 99 个只留 100 token 描述——context 从「全堆」变成「按需抽」。
🎯 关键认知

渐进披露把「知道有哪些 skill」和「知道 skill 怎么做」分开——前者只要描述（100 个共 10,000 token），后者用到才加载（1 个 2,000 token）。没有它，100 个 skill 的正文 200,000 token 会把 context 直接撑爆；有它，skill 可以装几十个而不拖垮主对话。

skill 和工具（tool）都能「帮 agent 做事」，可它们的分工到底差在哪？为什么不能只靠工具？
提示：想一想「连接」和「知识」两个词——工具连到了什么？skill 存下了什么？
▾
知识背景
skill 与 tool 是两个正交的层：tool（连接层，把「能调用的能力」暴露成函数：输入参数、执行、返回结果，MCP 就是这一层的协议）管「能不能连到某件事」；skill（知识层，把「怎么做」的流程与判断写下来）管「会不会做这件事」。一个 skill 内部可以调用工具，但它额外携带「何时用哪个工具、按什么顺序、遇到什么情况怎么办」的程序性知识。

上一张看到 skill 已是开放标准。这一张把它和工具的分工摆清。

因为「连到函数」和「知道怎么做」是两件事。就像一台能联网的打印机（工具）连到了打印功能，但「怎么排版、双面还是单面、打坏了怎么办」是操作手册（skill）。所以下面用一张表和一次任务的调用次数把两层分开。

🧮 第四笔账：连接层 vs 知识层
Step 1：两层一张表
层管什么例子
tool（连接层）能调用的能力MCP 的「执行命令」工具
skill（知识层）怎么做的流程「部署发布」skill
tool 暴露「能做」，skill 写清「怎么做」；skill 内部可以调 tool。
Step 2：一个部署任务，用工具要几次「猜」
方式模型要做什么
只有工具自己猜 3 步顺序、试错
有 skill按 1 条写好的流程走
只有工具时，模型要自己推「先测还是先部署」这 1 条关键顺序，容易错；skill 把它明确写下来，模型照着走。
Step 3：skill 是「用工具的方法」
关系说明
skill 调 tool流程里用工具执行每一步
tool 不依赖 skill工具单独也能被调
skill 是「怎么组合工具」的知识，工具是「单个动作」的能力，两者不是替代是互补。
🎯 关键认知

skill 与 tool 的分工 = 知识层 vs 连接层——工具把「能力」接进来（MCP 管这层），skill 把「怎么用这套能力」写下来。只有工具，模型每次都要自己推理流程（3 步顺序可能猜错）；有了 skill，流程被明确写下、可复用、可审计（要保证不跑偏仍需 hook 等硬约束）。这也是为什么「多工具」不等于「会做事」。

提示：回看第 44 课——subagent 的关键词是「隔离」，它有个独立 context；skill 呢，它的流程在哪条线程里跑？
▾
知识背景
skill 与 subagent 的分界（承接第 44 课 subagent）：skill 的流程在主对话线程里展开，你能看到并干预每一步，适合「复用固定流程」；subagent 跑在独立 context 窗口里，只回传结论，适合「隔离中间过程」。Anthropic 官方一句话：「用 subagent 隔离中间结果，用 skill 让流程在主线程里可看可调」（steering 博客）。

上一张分清 skill 与 tool。这一张和 subagent 划界：两者都能「做子任务」，但隔离性不同。

因为「复用流程」和「隔离过程」是两种需求。就像反复用的菜谱（skill）贴在厨房墙上、你照着一步步炒；而「去仓库翻 50 箱货找一样东西」是派个人去（subagent），他回来只报结果。所以下面用 context 账把边界算清。

Step 2：复用固定流程，skill 省多少

skill 复用流程只载描述 ≈100 token + 正文按需

固定流程反复用，skill 平时只占描述、用时加载正文；subagent 每次都要新开窗口、把所需背景重新写进委派说明，且过程不可见。

方式主 context 占用（示意）
读 50 文件全塞主窗口50 × 500 = 25,000 token
subagent 只回结论500 token
中间过程大、只要结论时用 subagent，省 24,500 token；默认在主线程里跑的 skill 做不到这点（过程全进 context）；Claude Code 里要隔离，可给 skill 设 context: fork，本质是交给 subagent 跑。
🎯 关键认知

skill 与 subagent 的边界 = 要不要隔离——复用固定流程用 skill（主线程、可见、省描述成本）；隔离中间过程用 subagent（独立窗口、只回结论、省 24,500 token）。把一个要「翻 50 个文件」的活写进 skill，中间草稿会撑爆主 context；把一个「每次一样的流程」交给 subagent，又要为固定流程每次新开窗口、重写委派说明，过程还看不见。
