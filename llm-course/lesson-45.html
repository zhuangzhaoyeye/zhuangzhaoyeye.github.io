第 45 课：Rule 规则

紧接第 44 课《Harness 运行时》：那一课把 agent 收成一句总纲——agent = 概率核心 + 确定性外壳。这一课只追一个问题——外壳上要装的第一件东西「约束」：LLM 每步输出都是概率采样、会越界，那「什么不能做、什么不能输出」这件事，怎么才能不靠模型自觉、而被真正「保证」？ 我们把 rule（规则，约束层）拆成三种形态——持久指令、生命周期钩子、并行 guardrail——一路算清「软 vs 硬」的分界、guardrail 并行与阻塞的代价，最后收口：rule 的本质，是把「什么不能变」从模型手里拿走，交给确定性代码。

🎯 学完这 6 步你将能够：
① 算清「靠 prompt 求模型别越界」的漏网率：单次照做 95%、跑 100 次漏 5 次，硬约束是 0
② 说清 rule 的三种形态（持久指令 / hooks / guardrail）各由谁执行、触发几次，并用「执行者是谁」划出软硬分界
③ 算出 guardrail 并行 vs 阻塞的账：时延 max(5,10)=10s vs 5+10=15s，以及并行白烧 800 token 的代价，并讲清 rule 的边界（不是鉴权、不是幂等）

↓
4既然「软硬之分」认定硬约束由代码执行、而代码也要花时间，所以 guardrail 这个硬约束就有了「并行 vs 阻塞」两种付账方式——并行省时延但可能白烧 token、阻塞省 token 但更慢。并行 vs 阻塞。
↓

↓
6既然「边界」划清了，所以收口：rule 干的就是把「什么不许变」从模型手里拿出来、交给确定性代码；下一步再把「怎么做」也沉淀成skill。

▾
知识背景
rule（规则，约束层，回答「什么不能做、什么不能输出」的那套机制）的对立面是「靠 prompt 软性约束」。这里有个绕不开的事实：模型每次输出都是采样——按概率分布抽一个 token，同一句提示它可能照做、也可能无视。Anthropic 官方文档直接写明：CLAUDE.md 这类指令「是上下文，而非强制配置」，要「无论模型怎么决定都拦下」得改用 PreToolUse hook（code.claude.com/docs/en/memory）。所以「求它别越界」只是改变采样概率，不是一道闸门。

上一课收口在「概率核心 + 确定性外壳」。这一张先问：约束能不能靠核心自己保证。

因为模型是概率采样，所以「求它别越界」只是软约束。就像对一个总忘事的人口头交代「千万别忘」——他大概率记得，但没保证；要有保证，得设一道他绕不过去的物理闸门。所以下面算一笔「软约束的漏网率」账。

🧮 第一笔账：靠 prompt 软约束，漏网多少
Step 1：模型每步是「采样」，不是「执行」
环节性质结果
决策概率采样同一提示可不同
工具执行确定性同一参数同一结果
模型负责的那一步是采样，所以「遵守规则」这件事本身也是概率的，不是必然的。
Step 2：软约束的「漏网」账
项数值（示意）
单次照做率95%（漏网 5%）
一天跑危险调用100 次
期望漏网100 × 5% = 5 次
算术：即使模型 95% 的概率会遵守，100 次里期望漏 5 次——软约束的保证是「大概率」，不是「一定」。
Step 3：软约束 vs 硬约束的漏网
约束方式性质100 次漏网
求它别越界软（靠采样）5 次
代码拦截硬（写死）0 次
软约束把保证押在模型这次采样上（漏 5 次），硬约束把保证押在写死的代码上（漏 0 次）。
🎯 关键认知

rule 解决的不是「让模型更听话」，而是「让约束不依赖模型听不听话」——软约束把保证押在采样上（100 次漏 5），硬约束把保证押在代码上（0 漏）。这就是「确定性外壳」在「约束」这件事上的具体含义。

因为约束要生效，必须有一个「确定性的东西」在某个时刻执行它。就像交通管制有三种落地方式：写在路口的告示牌（常驻提示）、红灯传感器（事件触发）、高速入口的安检（进出检查）。所以下面把三种形态对齐到「触发时机 / 谁执行 / 软硬」。

性质触发次数

真正「保证」的是后两类确定性代码（共 12 次硬拦截），持久指令只有 1 次且是软的。
🎯 关键认知

三种形态不是三选一，是分层——持久指令把规矩写进语境（软、量大、覆盖广），hooks 在动作前拦截（硬、每步），guardrail 在输入输出把关（硬、边界）。真正「保证不越界」的是后两类确定性代码，不是最显眼的那份指令。

知识背景
软硬的分界在「约束的执行者是谁」：写进 context 的指令（CLAUDE.md、rules、system prompt）由模型读取并「决定要不要遵守」——Anthropic 文档原话：CLAUDE.md 是「上下文而非强制配置」，要「无论模型怎么决定都拦下」得用 PreToolUse hook；而 hooks、guardrail 由 harness 的确定性代码执行，模型越不过去。一句话：执行者是模型 = 软，执行者是代码 = 硬。

上一张看到三种形态。这一张只追一个词：软 vs 硬。

因为「保证」这个词很重，只有确定性代码配得上。就像写进员工手册的「禁止」是软约束（有人会违反），刷卡门禁是硬约束（没卡就是进不去）。所以下面用「谁能绕过谁」把分界算清楚。

约束100 次危险调用漏网

Step 3：什么时候软约束也够用
风险例子够用吗
低（漏了不致命）命名规范软约束够
高（写生产 / 发请求）删库必须硬约束
软硬不是好坏，是按风险选——风险低的地方软约束就够，风险高的地方必须上代码。
🎯 关键认知

软硬的分界不是「语气强弱」，是执行者——模型执行的指令是软约束（可绕过、100 次漏 5），harness 执行的代码是硬约束（0 绕过）。所以判断一条规则靠不靠谱，只问一句：「它最后一步，是不是确定性代码在拦？」

guardrail 要跑一遍校验，可它和主 agent 谁先谁后？「并行跑」省时间，代价是什么？
提示：想一想「边开车边安检」和「安检完再发车」——前者快，但车已经开出去一段了；后者慢，但车没动。
▾
知识背景
OpenAI Agents SDK 的 input guardrail 有两种执行模式（官方文档 openai.github.io/openai-agents-python/guardrails/）：并行（默认 run_in_parallel=True，guardrail 与 agent 同时启动，时延最优，但 tripwire 触发时 agent 可能已消耗 token、执行了工具）；阻塞（run_in_parallel=False，guardrail 先跑完、agent 才启动，tripwire 触发则 agent 根本不执行，省 token 与副作用）。这是「时延 vs 成本」的经典权衡。

上一张分清软硬。这一张算「硬」的代价：guardrail 也要花时间。

因为校验有成本，并行和阻塞是两种支付方式。就像安检：边排队边安检（并行）快，但坏人可能已经过了闸；先安检再放行（阻塞）慢，但坏人进不来。所以下面算并行 vs 阻塞的时延与 token 账。

🧮 第四笔账：guardrail 并行 vs 阻塞
Step 1：两种模式的时序
模式谁先启动tripwire 触发时 agent 状态
并行同时可能已烧 token / 执行工具
阻塞guardrail 先未启动（0 消耗）
并行让 agent 先跑着，阻塞让 agent 等校验通过才跑——这是两种时序。
Step 2：时延账
模式算式总时延（示意）
并行max(5, 10)10s
阻塞5 + 1015s
算术：guardrail 5s、agent 10s。并行取两者较大值 max(5,10)=10s，阻塞串行相加 5+10=15s，省 5s。
Step 3：成本账（tripwire 触发时）
模式恶意输入下 agent 消耗
阻塞0 token（未启动）
并行可能已烧 800 token（示意）
阻塞在恶意请求下 agent 0 成本；并行里 agent 可能先烧了 800 token 才被叫停，差 800。
🎯 关键认知

并行与阻塞不是「哪个对」，是拿时延换确定性——并行把时延压到 max(5,10)=10s，代价是 tripwire 晚一步、可能白烧 800 token；阻塞先验后跑，恶意请求 0 成本，但每次都要等满 5+10=15s。贵的模型 + 高风险选阻塞，便宜 + 高吞吐选并行。

rule 是兜底，不是万能保险。它拦的是「模型这一步的概率输出越界」，管不了两件事：鉴权（谁有权做，是身份 / 权限系统的事，rule 只能在你已经拿到权限之后、在动作上再卡一道）与幂等（同一操作重复执行结果一致，是操作语义本身、靠工具设计保证，rule 拦不了「重复提交」）。把这两件事甩给 rule，是最常见的误用。

上一张算清 guardrail 的账。这一张给 rule 划边界：它再硬，也有管不到的。

因为rule 只在一个动作「要发生的那一刻」拦，它不管「你是谁」、也不管「这动作做两遍会怎样」。就像门禁能拦住没卡的人，但拦不住「有卡的人一天刷 10 次」（那是权限和计费系统的事）。所以下面把「rule 能管 / 管不了」对齐。

🎯 关键认知

rule 的边界 = 它只在「动作要发生的那一刻」起作用——管「这一步该不该发生」，不管「你是谁」（鉴权）、不管「做两遍是否一样」（幂等）。把这些甩给 rule，等于在门禁上堆了一堆它天生看不见的东西，防线反而漏。
