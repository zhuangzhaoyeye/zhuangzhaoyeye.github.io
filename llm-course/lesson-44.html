第 44 课：Harness 运行时

紧接第 21 课《从 Prompt 到 Agent》：那一课把 agent 拆成「模型 / 工具 / 状态 / 终止条件」四件套，讲清了「循环长什么样」。这一课只追一个问题——四件套是一张还没通电的逻辑图，还是已经跑起来的 Agent？ 我们从「LLM 只是一次前向计算」讲起，把 harness（编排运行时）必须管的六件事——状态、工具执行、权限、恢复、隔离、兜底——一路算到最底层的收口：agent = 概率核心 + 确定性外壳。

🎯 学完这 6 步你将能够：
① 算清「一个 10 步循环里，模型做了几步、剩下的谁在做」：10 步 × 3 动作 = 30，模型只做 10 个决策，harness 接管 20 个
② 说清 harness 最小三职责（状态 / 工具执行 / 权限），并算出「第 19 步失败从头重跑要白花 18,000 token、有 checkpoint 只重跑 1,000」
③ 用「subagent 隔离」算出读 50 个文件只回传结论，主 context 省 24,500 token，并解释 hooks（PreToolUse / PostToolUse）为什么是确定性兜底

▾
知识背景
第 21 课定义了 agent 循环的四件套，但那是在讲「循环长什么样」。工程上有个更底层的事实：LLM（大语言模型，输入 token 序列、输出 token 序列的一次前向计算）本质上只做一次「读进 → 吐出」，算完就结束，既没有「下一步该做什么」的意识，也没有「状态」这种概念。harness（编排运行时，负责驱动 agent 循环、管理状态并执行工具的那层确定性软件）要回答的正是「谁来驱动这个循环往下走」。

上一课把 agent 拆成了四件套。这一张先问一个更底层的问题：这四件套，谁在「跑」它。

因为模型只会做一次前向计算，所以「跑循环」这件事不能靠模型自己。就像一台只会在「收到纸条 → 回一张纸条」的自动回信机：它不会把纸条递给下一个人，也不会记下刚才聊过什么——要有一个人（harness）在中间收纸条、递纸条、记状态。所以下面算一笔账：一个 10 步任务里，模型到底做了几步，剩下的谁在做。

🧮 第一笔账：一个 10 步循环里，模型做了几步
Step 1：循环的每一步，拆成三个动作
动作谁做说明
决策模型（LLM）读 context、吐下一步
工具执行harness解析参数、调函数、拿结果

Step 2：10 步任务一共有多少个动作
项数值

模型做的（决策）10 个
harness 做的（工具 + 状态）10 × 2 = 20 个
算术：10 步任务里模型只做了 10 个决策，剩下 20 个动作（工具执行 10 + 状态更新 10）由 harness 接管。
Step 3：没有 harness 时，那 20 个动作谁来补
方式模型做人手动做harness 接管
手动喂10 次决策20 个动作全手动0
有 harness10 次决策020
没有 harness 时，工具执行与状态更新这 20 个动作都得靠人手动补；有了 harness，它们被程序接管，循环才真正「自动」起来。
🎯 关键认知

harness 解决的不是模型能力问题，而是「循环谁来驱动」——没有 harness，你只能自己手动把每次工具结果拼回去、再发起下一次调用；有 harness，那 20 个动作被程序接管，agent 才从「一张逻辑图」变成「一个跑起来的系统」。

知识背景
harness 的最小职责可以归纳成三件：状态（把工具结果拼回 context、维护记忆，让循环知道「刚才做了啥」）、工具执行（解析模型吐出的参数、调函数、拿结果）、权限（每个动作在落地前过一道门）。这三件不是某个标准名词，而是从第 21 课四件套直接推出的最小闭环；Claude Code 的 harness 与 OpenAI Agents SDK 的 Runner 做的都是这三件事。

因为循环要往前走，三件事缺一件就会断或失控。就像开一条自动流水线：得有人管「工件到哪个工位了」（状态）、「这台机器怎么开」（工具执行）、「哪些操作要按急停」（权限）。所以下面把三件事摊开，并算「权限门」与「结果回填」两笔账。

🧮 第二笔账：跑起来要管的三个必要条件

项数值

项数值

🎯 关键认知

harness 的三件职责是「与」的关系：有状态 → 循环记得刚才；有工具执行 → 决策能落地；有权限 → 动作被约束。任何一件缺了，harness 都不成立——这就是为什么「跑循环」三个字背后，其实是一套必须齐全的确定性职责。

循环跑起来了，但跑到第 19 步失败了——从头重跑的话，前面 18 步是不是全白做了？
提示：先算一笔账——那 18 步已经花掉的 token，能不能不重新花？

知识背景
harness 不能只「跑」，还得「跑得能恢复、能定位」。三件事：checkpoint（检查点，把某一步的完整状态存下来，失败后从这里恢复而不是从头）、重试（失败后按策略再试）、追踪（trace，记录每一步的输入输出，出问题能定位到哪一步）。这三件是 LangGraph、Google ADK 这类 harness 都内置的能力——例如 LangGraph 的 checkpointer（状态快照器）就是 human-in-the-loop（人在环）与断点恢复的前置条件。

上一张卡片把循环跑起来了。这一张处理「跑一半失败了怎么办」。

因为真实任务会失败，从头跑 = 白花前面已算的 token。就像写长文档时随手 Ctrl+S 存盘，软件崩了从最近的存档继续，而不是重打全文。所以下面算一笔「重跑 vs 恢复」的账。

🧮 第三笔账：从头重跑 vs 断点恢复

项数值（示意）
单步 context1,000 token

处理重跑步数多花 token
从头重跑19 步19 × 1,000 = 19,000

项无 trace有 trace

算术：没有 trace，20 步里哪步错了要逐个人肉排查；有 trace，直接看到第 19 步的输入输出，定位代价从 20 步压到 1 步。
🎯 关键认知

checkpoint 把「失败成本」从「重跑全程」降到「重跑最后一步」——没有它，20 步任务在第 19 步失败，前 18 步的 18,000 token 就白花了；有它只重跑第 19 步的 1,000，省 18,000。这就是 harness 的「可恢复性」：跑得快不如摔得轻。

一个 agent 的 context 窗口是有限的，可真实任务要看几十个文件、跑几十条命令——这些中间过程往哪放？
提示：想一想——「为了回答一句话而翻遍代码库」的过程中，哪些信息必须留在主对话里，哪些只是路上的草稿？
▾
知识背景
subagent（子智能体，一个拥有独立 context 窗口的助手：主 agent 把子任务委派给它，它在自己的窗口里工作，最终只把结论返回）是 harness 提供的一种「上下文隔离」机制。Claude Code 内置了 subagent（如 Explore 这类偏只读搜索的、Plan 这类在 plan 模式下为制定计划做只读调研的），目的正是让主 context 不被中间过程撑爆——几十个文件、几十条命令的过程数据留在 subagent 自己的窗口里，主 context 只多占回传结论的那一小段。

上一张卡片解决了「跑得能恢复」。这一张处理横向压力：context 装不下怎么办。

因为主 context 是稀缺资源，中间过程不该进主窗口。就像让实习生去档案室翻 50 份文件、回来只交一页摘要，而不是把 50 份文件全堆你桌上。所以下面算 subagent 隔离能省多少 context。

项数值（示意）

每个文件500 token
中间过程总量50 × 500 = 25,000 token
算术：读 50 个文件、每个约 500 token（示意），中间过程就是 25,000 token。

方式主 context 占用
把 50 个文件全塞进来25,000 token

算术：subagent 把 25,000 token 的中间过程压成 500 token 的结论，主 context 省下 24,500 token。

项全塞只回结论

🎯 关键认知

subagent 把「过程」与「结论」分开——有它，主 context 只装结论、省下 24,500 token；没它，中间草稿把主窗口撑爆，agent 越跑越「健忘」，长任务尤其明显。这是 harness 提供的「上下文隔离」，也是第 48 课 Claude Code「context-first」思路的种子。

知识背景
hooks（钩子，在 agent 生命周期关键点自动触发的一段确定性脚本）是 harness 的「确定性兜底」。Claude Code 的 hooks 在生命周期各点注册 shell 命令：PreToolUse 在「模型创建好工具参数之后、真正执行工具之前」运行，PostToolUse 在工具成功完成后运行，常见匹配器有 Agent（子代理任务，旧名 Task）、Bash（shell 命令）等。它们的共同点是：触发时机固定、逻辑写死，不依赖模型「自觉」。

上一张卡片用 subagent 管住了规模。这一张管风险：模型每步都是概率决定，越界不能靠它自觉。

因为模型输出不确定，越界不能靠「希望它守规矩」。就像自动门在「人靠近」这个事件上装传感器（hook）触发开关门——hook 就是挂在「某个事件发生」上的确定性动作。所以下面算 hook 拦下多少越界动作。

🎯 关键认知

hooks 是确定性兜底：模型这一环是概率的、可能越界，hook 这一环是写死的、必然触发——有它，越界动作在发生前被拦；没它，只能事后补救。这正是下一课要展开的「rule（规则）」的雏形：把「什么不能变」从模型手里拿出来，交给确定性程序。

把前面五张卡合起来看，harness 到底是个什么东西？它和「agent」是什么关系？
提示：用一句话收口——前面讲的那几件职责（状态 / 工具 / 权限 / 恢复 / 隔离 / 兜底），都是在给谁「搭壳子」？
▾
知识背景
把 harness 的职责收敛成一句总纲：agent = 概率核心 + 确定性外壳。概率核心是 LLM（不确定、会犯错、每步都是采样），确定性外壳是 harness（写死、可依赖、可审计）。这是理解后面第 45–48 课的钥匙：rule（规则）、skill（技能）、开放标准，都是在往这个外壳上继续装东西。

前面五张卡把「外壳」一层层搭起来：谁在跑（驱动）、三职责（状态 / 工具 / 权限）、恢复、隔离、兜底（hooks）——它们都是同一个「外壳」的组成部分。

因为核心不可靠，所以要一个可靠的外壳把它包起来。就像自动驾驶 = 神经网络（感知/决策，概率）+ 一套确定性控制器（刹车、限速、护栏，写死）。所以把这几件职责收成一张表，并预告「外壳还能装什么」。

🎯 关键认知

agent 不是「一个更聪明的模型」，而是「一个概率核心 + 一个确定性外壳」。外壳越厚，越能把核心的不确定性关进笼子——这就是为什么第 45 / 46 / 47 课分别讲 rule、skill、标准：它们都是往这个外壳上继续装东西，第 48 课再回头用这个总纲评判四家 harness 各选了哪条路。
