第 18 课：推理引擎

前面几课我们把模型"调好"了——切分、省显存、量化、微调。这一课换个视角：把它发出去服务几百个并发用户。一个请求要分两段跑（prefill 与 decode），两段的瓶颈完全不同；把请求一条条串起来处理会把 GPU 饿死，于是有了批量、连续批处理、分页 KV。这一课把吞吐翻倍背后的四件机制算清，最后回答一个工程问题：vLLM（即用分页 KV 与块级前缀缓存做高吞吐的通用推理引擎）/ SGLang（即用 token 级前缀树复用共享前缀的推理引擎）/ TensorRT-LLM 到底怎么选。

🎯 学完这 6 步你将能够：
① 用算术强度说清 prefill 与 decode 为什么卡在不同的硬件资源上
② 算出批量、连续批处理、分页 KV 各自把吞吐抬高了多少，并说清代价
③ 按负载特征（共享前缀 / 模型是否固定 / 延迟还是吞吐）选对推理引擎
🗺 本节推理链（6 步逻辑递进：从"请求两段"到"选型决策"）
1要让一张 GPU 扛住几百个并发请求，必须先看清一个请求在引擎里被拆成两段——这就要求知道 prefill 一次算完整段输入、decode 每次只算 1 个 token，两者的算术强度差三个数量级。两段瓶颈不同。
↓
2既然「两段瓶颈不同」，所以decode 每步只算 1 个 token、却要把整份权重读一遍，算力在干等数据——于是要把多条请求凑成一批，用同一份权重顺带算很多个 token，把带宽的固定成本摊薄。靠批量填满算力。
↓
3既然「靠批量填满算力」，所以批怎么组就成了关键——静态批要等最长的那条、把短请求拖成陪跑；这就要求改成按 iteration 组批：每一步谁吐完 token 谁就让位、新请求立刻补上。批要动态进出。
↓
4既然「批要动态进出」，这就要求显存里同时塞下很多条的 cache（KV）——而它又大又是动态增长的，按最大长度预留会浪费一大半；于是把 KV 切成固定大小的块、按需分配（分页即 PagedAttention，就是把 KV 按固定块管理）。KV 要按块分页。
↓
5既然「KV 要按块分页」，所以调度器就有了一个统一目标——不浪费：显存不够时在「换出（swap）」与「重算（recompute）」之间取舍，重复计算时用前缀缓存复用共享的 cache。调度要在不浪费上取舍。
↓
6既然「调度要在不浪费上取舍」，而"省哪种浪费"正是各引擎的侧重所在，这就要求先弄清自己的负载"浪费在哪"——重复前缀多就该选 token 级 cache 树（SGLang），模型固定且只用 NVIDIA 该选编译优化（TensorRT-LLM），多模型多硬件才选通用 vLLM；长 prefill 打断 decode 时再考虑 prefill/decode 分离。按负载选引擎。

1
同一张 GPU 上，为什么一个请求"算完输入"和"逐字往外吐"的瓶颈完全不是一回事？
提示：把两段各自的 FLOPs 和要读的字节数分别算出来，比一比它们的比值（算术强度）。
▾
知识背景
一次自回归推理被切成两段：prefill（把整段输入 prompt 一次并行算完、产出第一个 token，决定 TTFT 首字延迟）与 decode（此后每次只算 1 个新 token、逐字生成，决定 TPOT 每字延迟）。这条切分是 vLLM（Kwon 等，arXiv:2309.06180，SOSP 2023）与 Sarathi（Agrawal 等，arXiv:2308.16369）共同的工作基础。判断一段计算卡在算力还是带宽，用一个量：算术强度 = FLOPs ÷ 访问字节数；超过 roofline 拐点（拐点 = 峰值算力 ÷ 显存带宽）就是 compute-bound（算力受限），低于就是 memory-bound（显存带宽受限）。

上一课我们把模型"调"成了自己的；从这一课开始，我们把它发出去服务。一个请求进推理引擎，会依次过：分词 → 排队调度 → prefill → decode → 反分词 → 流式返回。要扛住并发，第一件事是看清这条路里哪一段在吃 GPU 的什么资源。

因为prefill 一次吃下整段 prompt（一大块矩阵-矩阵乘），decode 每次只吃 1 个 token（退化成矩阵-向量乘）——两者对 GPU 的压力完全不是一回事。可以把它类比成搬运：prefill 是一次装满一整卡车货（算力吃紧），decode 是一次只搬一个箱子、却要把整个仓库的目录重读一遍（带宽吃紧）。混在一起"加算力"，对 decode 几乎没用。

下面把两段的算术强度各自算出来，就会看到那条分界线。

🎯 关键认知

把 prefill 与 decode 混为一谈，会做出错误的优化决策：给 decode 堆算力（没用，它等的是数据），或给 prefill 堆带宽（也没用，它等的是计算）。"先分清一段计算卡在哪个资源上"，是推理引擎里所有取舍（批量、调度、分离）的前置判断。

同样一张 GPU，为什么把请求一条条串起来处理就快不起来？
提示：把"每步要读多少字节"和"每步只产出几个 token"放在一起看，瓶颈会自己冒出来。
▾
知识背景
上一张卡片已经说明 decode 是显存带宽受限。提高利用率的标准手段是批处理（batch）——Databricks 的《LLM Inference Performance Engineering》把"连续批处理"列为高吞吐服务的首要优化，并报告它比早期的动态批处理高 10-20 倍吞吐。理解批量的第一步，是看清单条 decode 的固定成本：读一遍权重的时间，与批里有多少条请求无关。

上一张卡片看清了 prefill 与 decode 卡在不同资源上。这一张从 decode 的"固定成本"入手，说明为什么逐条处理会把算力白白闲置。

因为decode 每生成 1 个 token 都要把整份模型权重从显存读进计算单元——这段读取时间对批里是 1 条还是 64 条几乎一样。把多条请求凑成一批，就像让这趟"读权重的车"顺路多捎几个 token。所以批越大，单位时间内吐出的 token 越多，而每条请求的延迟几乎不变。反过来，一条条串行处理（更自然的做法是让一条请求从头跑到尾、再接下一条），等于每读一次 14 GB 只换来 1 个 token——单卡吞吐只有约 143 token/s，而同一张卡批 64 时可达约 9,143 token/s（第 2 步算例），64 倍差距里大部分算力都在等数据。

下面把"批大小"对吞吐的放大效应算出来，同时看清静态批的隐藏浪费。

🎯 关键认知

批量靠"摊薄读权重的固定成本"把吞吐抬高一个数量级。但批量本身有代价：一旦按"一批"为单位调度，批里最长的那条就成了整批的枷锁。所以真正的解法不是"批得更大"，而是"批得更聪明"——让请求按步进出，而不是按批被钉死。

3
为什么同样的负载，换个组批方式吞吐就差好几倍？
提示：想一想静态批里，短请求吐完之后那段空着的位置在干什么——能不能让它别浪费？
▾
知识背景
连续批处理（continuous batching / iteration-level scheduling）由 Orca（Yu 等，2022）提出，核心是"请求可以在单个 iteration 的粒度上进出一个批次"。vLLM（arXiv:2309.06180）把它与 PagedAttention 结合，成为当前主流的服务范式。Databricks 的工程指南报告：连续批处理相比静态/动态批处理可高 10-20 倍吞吐。

上一张卡片看到静态批被最长序列绑架。这一张回答解法：把批次从"一批"降级到"一步"来管。

因为自回归生成天然是"一步一个 token"的循环，调度器完全可以在每一步结束时重新决定：哪些序列已经吐完（遇到停止符或到长度上限）就立刻让位，排队里的新请求立刻补进空槽。所以短请求不再陪跑——它一吐完就腾位置给下一个，8 个槽位几乎每步都满。就像流水线上的工位：谁手里的活做完就下、新任务立刻补上空位。这就是"连续"的含义：批次是流动的，不是固定的。

更自然的做法是静态批：凑齐 8 条一起跑、等最长的那条跑完再收工——但上一张卡片的算例里，8 个槽位只有 13.9% 的时间在干活，剩下 86% 全浪费在陪跑上。连续批处理要解决的，正是这 86%。

🎯 关键认知

连续批处理没有让单条请求变快（它仍是带宽受限），它改变的是槽位利用率——把"陪跑浪费掉的时间"还给真正在生成的请求。它也是后面分页 KV、前缀缓存能生效的前提：只有批能动态进出，才需要"按需分配与回收显存"。

分页 KV 到底解决了哪个看不见的工程问题？
提示：KV cache 又大又是动态增长的——如果按"最大长度"给每条预留空间，预留出来却没用上的那部分，算不算浪费？
▾
知识背景
vLLM 的 PagedAttention（Kwon 等，arXiv:2309.06180，SOSP 2023）把 KV cache 切成固定大小的块（block），用块表把连续的逻辑块映射到非连续的物理块——就像操作系统用页表管理内存。vLLM 官方博客给出的对照读数：既有系统因碎片与过度预留浪费 60%-80% 显存，PagedAttention 把浪费压到 4% 以下，并能跨请求共享块（并行采样等场景内存再降最多 55%）。

上一张卡片让批次能动态进出，前提是显存里同时装得下很多条请求。这一张回答：KV cache 到底占了多少、又被浪费了多少。

因为KV cache 的大小随序列长度增长，而每条要生成多长事先并不知道。朴素做法是"给每条按最大长度 max_len 预留一块连续显存"——结果实际只用了其中一部分，剩下的空着（内部碎片）；不同长度的请求交错分配，又会留下零散的、装不下新请求的空洞（外部碎片）。PagedAttention 的做法是：不再要求连续，把 KV 切成固定大小的块，用到哪块分配哪块，用一张"块表"把逻辑位置映射到任意物理块。

朴素做法正是按最大长度预留：一条序列最多可能生成 2048 token，就一次性给它留足 2048 个位置；可它实际可能只生成 512——剩下的 1536 个位置一直空着，白占 75%。不改掉这套「一次连续预留」的做法，显存就永远装不下更多请求。

5
显存不够时，调度器凭什么决定抢占谁、缓存谁？
提示：抢占只有两条路——把 KV 换出到内存（swap）或直接丢掉重算（recompute）；两条路的代价要用带宽和算力分别算。
▾
知识背景
vLLM 的调度器在显存不足时会抢占（preempt）某些请求，方式有两种：swap（把该请求的 KV 块换出到 CPU 内存，之后再换回）或 recompute（直接丢弃 KV，等它重新被调度时把 prefill 再算一遍）。另一条线是前缀缓存：vLLM 的块级自动前缀缓存、SGLang 的 RadixAttention（arXiv:2312.07104，用基数树做 token 级前缀复用、LRU 淘汰，报告前缀密集负载最多 6.4× 吞吐）。

上一张卡片解决了"装得下"。这一张处理真的装不下时——调度器要在两条代价路线上做取舍，顺便把"重复计算"也省掉。

因为显存是硬的：当新请求要进来而 KV 池已满，调度器必须腾地方。腾地方有两条路（就像仓库满了：先把最不常用的箱子搬到隔壁房间，或者干脆扔掉、需要时再重新组装）：把某条请求的 KV 换出到 CPU 内存（swap，付出带宽代价），或者干脆丢掉它的 KV、等它再次被调度时重算一遍 prefill（recompute，付出算力代价）。选哪条，取决于此刻带宽和算力谁的性价比更高。另一头是前缀缓存：很多请求共享同一段 system prompt / 工具说明，把它们算过的 KV cache 缓存起来复用，就能省掉大量重复 prefill——这就是 SGLang RadixAttention 的主场。

不缓存就只剩更笨的一条路——每条请求各算各的：一段 2000 token 的 system prompt 被 100 条并发请求共享时，不做前缀复用就要重复 prefill 100 × 2000 = 200,000 token，其中 99% 是纯重复。前缀缓存要省掉的正是这 99%。

🎯 关键认知

调度器的目标从"公平"变成了"不浪费"：显存紧张时在 swap（带宽）与 recompute（算力）之间选便宜的那条，平时则把共享前缀缓存下来避免重复计算。这也解释了为什么"共享前缀多"的负载（多轮对话、RAG（即检索增强，把外部资料检索出来塞进上下文）、Agent 循环）特别吃前缀缓存——它们的重复计算占比高得惊人。

6
vLLM / SGLang / TensorRT-LLM，凭什么选 A 不选 B？
提示：先别比"谁更快"。问自己两个问题：你的流量里有没有一段反复出现的公共前缀？模型是不是长期固定、只用一种卡？
▾
知识背景
主流推理引擎各有侧重：vLLM（PagedAttention + 块级自动前缀缓存，通用、模型与硬件覆盖广）、SGLang（RadixAttention，token 级前缀树，前缀复用强，报告前缀重负载最多 6.4×）、TensorRT-LLM（NVIDIA 专用、编译期优化，追求极致延迟）。另一条工程线是 PD 分离（prefill/decode disaggregation）：把计算受限的 prefill 与带宽受限的 decode 拆到不同 GPU 上跑。

前面五张卡片把单机引擎的机制讲完了：两段瓶颈、批量、连续批处理、分页 KV、调度取舍。这一张回答落地时最实际的问题——选哪个引擎。

因为引擎的差异不体现在"谁绝对更快"，而体现在"你的负载长什么样"。四个判断维度：① 共享前缀多不多（多 → SGLang 的 token 级前缀树收益最大）；② 模型是否固定、是否只用 NVIDIA（固定 → TensorRT-LLM 的编译优化能榨出更低延迟）；③ 是否要覆盖多模型/多硬件（要 → vLLM 更通用）；④ TTFT（首 token 延迟）与 TBT（Time Between Tokens，相邻两个输出 token 的间隔，即逐字延迟）哪个是硬约束（长 prompt 会打断在跑的 decode，可考虑 PD 分离）。这就好比选运输工具：通用货车、冷链专车、还是固定线路的直达快线。

🎯 关键认知

选型三步：① 先量自己负载的前缀命中率与 SLO（Service Level Objective，服务水平目标，即 TTFT / TBT 这类硬指标）；② 按"共享前缀多不多、模型是否固定、要不要多硬件"挑引擎；③ 只有当长 prefill 的干扰真的踩到 TBT 红线时，才上 PD 分离。到此，"训练与推理工程"这条线收口——下一课我们把"模型好不好"这件事本身，变成可核验的评测。
