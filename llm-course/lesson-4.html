第 4 课：Tokenization 机制

模型不识字，只看数字。把"我爱吃苹果"这五个汉字变成模型能理解的数字序列——这一步叫 Tokenization。不同的切法直接影响模型的理解力、推理速度和显存开销。

🎯 学完这 6 步你将能够：
① 亲手推演 BPE 算法的合并过程，说出"为什么 lo 要和 w 合并"
② 算出中文比英文多多少 token，解释"多语言税"的来源
③ 说出词表从 32K 扩大到 152K 的 Embedding 层代价，判断值不值得
🗺 本节推理链（6 步：从「词表有限 + 要能表示任何字符串」逼出子词切分）
1为什么要切？ — 从「我爱吃苹果」出发：模型只吃整数 ID，而「什么算一个词」没有共识——切太粗会撞生词（[UNK]），切太细序列又太长，于是要找一种「有限词表内、可复现」的 token 单元
↓
2切法怎么学到？ — 规则靠人工拍脑袋定不下来，所以要让它从语料里长出来：反复合并最高频的相邻符号对，这就是 BPE，每个合并出的新符号也是一个 token
↓
3为什么中文更费 token？ — 词表容量有限、训练语料却英文占多数，所以同样的意思中文要更多 token（多语言税），代价落在上下文窗口和成本上
↓
4词表多大才划算？ — token 越少推理越省，但词表越大 Embedding 参数越多，所以要在「省 token」和「省参数」之间算一笔账（32K vs 152K）
↓
5不出 [UNK] 就没问题了吗？ — 切出来的单元得是训练里见过的，所以见得极少的「幽灵 token」会让输出失控（重复、乱码），逼出词表清洗与重复抑制
↓
6把口径冻结成一份词表，链路才闭合 — 幽灵 token 说明「切出来的必须是训练里见过的」，因此词表一旦冻结就不能随意新增；于是训练 tokenizer、编码、推理、解码四步必须共用同一份词表，整条链路才自洽

"我爱吃苹果"五个汉字——模型是怎么把它们变成一串数字的？
提示：模型内部只有矩阵乘法，只能吃数字。中文不像英文可以按空格分——"吃"和"苹果"之间没有天然的分隔符。
▾
知识背景
Tokenization 是人类文本与模型数学之间的桥梁——模型只吃数字，不吃字符。子词分词（Subword Tokenization）在 2016 年左右成为标准（Sennrich et al.），替代了词级分词（OOV 问题）和字符级分词（序列过长）。BPE（GPT 系列）、WordPiece（BERT）、Unigram（T5 采用的算法）是三大主流子词算法；它们常由 SentencePiece 这类分词库实现——SentencePiece 是库（支持 BPE 与 unigram 两种算法），本身不等于某一种算法。

Transformer 的输入不是文字，是一组整数 ID。把文本切成 token、再映射到 ID 的过程就是 Tokenization。不同切法天差地别：

按字切 — "我/爱/吃/苹/果" 5 个 token，信息太散
按词切 — "我/爱/吃/苹果" 4 个 token，但"苹果"要事先在词表里
按子词切 — "我/爱/吃/苹果"（中文可能是 1-2 字一组），这是现代大模型的主流方案

Tokenization 就像给一本没有目录的书编页码：页码（token）编得太细，翻页次数暴增；编得太粗，一页里混着好几件事。模型的上下文窗口就是这本书能翻的页数——所以「页码怎么编」直接决定它一次能读多少内容。

为什么不直接用「整词表」或「单字符表」？两头都会撞墙：按单字符切，英文「I love apples」会变成 11 个 token（而按词只要 3 个），序列一长注意力计算量按长度平方增长；按整词切，只要遇到没进词表的「apples」，就直接变成 [UNK]、信息全丢。子词是唯一能同时躲开这两头的切法。

🎯 核心矛盾

切太细（按字符/字节）→ token 序列太长，Attention 复杂度 O(n²) 受不了；切太粗（按词）→ 词表爆炸，新词变 [UNK]。BPE 的子词方案是这两者的平衡点——用高频子词覆盖常见表达，用低频组合拼出新词。

知识背景
BPE = Byte Pair Encoding。最初由 Gage（1994）用于数据压缩，Sennrich et al.（2016）引入 NLP。核心：迭代合并最频繁相邻符号对，从字符（byte-level 实现则从 256 个字节）开始逐步构建子词，最终形成词表。GPT-2/3/4、Llama、RoBERTa 均使用 BPE。SentencePiece 和 HuggingFace Tokenizers 是主流实现。

上一张卡片我们理解了为什么需要 tokenization——把文本切成 token 再映射到整数 ID。BPE 是最主流的子词切分算法：从字符级开始，反复合并最频繁的相邻符号对。下面从零推导一遍它的合并过程。

BPE 好比整理一堆积木：先按字母把积木摊开，然后每次都把「挨在一起、出现最多」的两块粘成一整块，直到词表装满——没见过的「apples」也能用粘好的「apple」加「s」拼出来。

🎯 为什么 BPE 优于固定词表？

本卡语料只有 low / lower / lowest，但测试时遇到 "lowers" 也能切：BPE 会把它切成 lower + s（lower 和 s 都在最终词表里）。只要能拼出没见过的新词，就永远不会输出 [UNK]。

知识背景
BPE 天然适应空格分隔的语言（英文）。中文无自然词边界 + 每个字 3 字节 UTF-8 编码 → 同样语义下中文 token 数比英文多 50%-80%（依 tokenizer 而异，估算）。这是 tokenization 领域的持续争议：统一算法 vs 语言定制。Qwen（通义千问）通过大词表（152K）+ 显著提高的中文语料比例大幅缓解了这一问题。

上一张卡片我们走通了 BPE 从字符开始合并出子词的完整过程。现在看看这种机制对不同语言的影响：同样的意思，中文消耗的 token 通常比英文多 50%-80%。这是因为 BPE 训练数据以英文为主，"apple" 被合并成了一个 token，而"苹果"的两个字可能还没被合并——或者更糟，被拆成字节级碎片。

想象一下用一本只收英文词的小字典查中文——「苹果」查不到，只能一个字一个字（甚至一个字节一个字节）地翻。这就是中文在英文优先 tokenizer 下的处境，也是多语言税的来源。

🎯 为什么中文 tokenizer 普遍更差？

因为 BPE 是在训练数据上统计的——训练数据里英文占绝对多数。英文的 "the" 出现了几百万次，早就被合并成一个 token；中文的"的"虽然频率也高，但因为 UTF-8 编码占 3 字节，BPE 可能需要先合并字节再合并字再合并词——层级更多、合并更慢。这就是为什么 Qwen 要专门为中文训练自己的 tokenizer，把词表做到 152K（相比 Llama 的 32K 大近 5 倍）——就是为了减少中文的"多语言税"。

知识背景
文本退化（Text Degeneration）由 Holtzman et al.（2019，"The Curious Case of Neural Text Degeneration"）系统记录。现象：模型在长文本生成中陷入重复循环。根因是解码策略——贪心地逐 token 取最高概率（或 beam search 最大化似然）会把分布长尾排除掉，生成因此陷入高概率循环；tokenization 与 Attention 会放大这一现象，但不是根因。解决：nucleus sampling（top-p）、temperature scaling、repetition_penalty——已成为 LLM 推理标准配置。

前面我们讨论了 tokenization 的效率（token 数量）和代价（Embedding 参数）。但它还有一个更隐蔽的影响：某些 token 的编码方式会让模型陷入「退化循环」——不停重复同一个词或符号。

这就像一列火车在环形轨道上跑——只要某个高频 token 让上下文又回到「和刚才几乎一样」的状态，模型就会沿着同一条轨道再跑一圈，于是重复同一个词。这种循环在论文里叫文本退化（text degeneration）。

2023 年（Rumbelow & Watkins，LessWrong 报告）发现的 "SolidGoldMagikarp" 问题：Reddit 用户名被 tokenizer 单独编码，但训练数据里只出现几次——模型对这个 token 的理解是"随机噪声"。只要你输入这个用户名，模型就会产生不可预测的输出。
🎯 怎么缓解？

现代 tokenizer 的改进方向：① 增加词汇表大小（让常见组合被合并，减少单字 token）；② 训练时加入更多样化的数据（避免某个 token 只在窄领域出现）；③ 推理时加 repetition_penalty（对已出现的 token 降权，打断重复循环）。注意：①② 在 token 侧减少诱因，③ 直接作用在解码上；而重复循环的根因是解码策略，所以 ③ 类手段最直接对症。

关键在于：token 同时是钱（按量计费）和上下文窗口（额度有限）。这些你看不见的标记照样被计费、照样挤占窗口。这就像寄快递——你写的信只占包裹一角，面单、填充物、封条都是系统加的，但它们一样要称重、一样算运费。
